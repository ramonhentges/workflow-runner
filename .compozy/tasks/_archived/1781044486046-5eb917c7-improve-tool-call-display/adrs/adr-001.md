# ADR-001: Model tool calls as a first-class, identity-bearing run event

## Status

Accepted

## Date

2026-06-08

## Context

Agents driven through ACP emit a lifecycle of updates for every tool they
invoke (e.g. a `bash` command, a file read, a file edit). Each call begins
"pending", transitions to "in_progress", and ends "completed" or "failed".
Today these updates are flattened into generic free-text log lines, so:

- The user sees three or more disconnected lines per call (e.g.
  `Tool: bash (pending)`, then `Tool: call_00_…: in_progress`, then
  `Tool: call_00_…: completed`).
- The stable identifier that ties those updates together is never surfaced as
  a meaningful concept, so neither the CLI nor the web UI can recognise the
  updates as belonging to the same call.
- Rich context the agent already provides — the kind of action, a
  human-readable summary, the command, the file path, the failure reason — is
  discarded.

The product goal is a single, self-updating entry per tool call in BOTH the
CLI/TUI and the web UI: an icon/spinner that reflects status, a readable
summary of what the agent did, and a failure reason when one occurs. Users
also expect this to look identical whether they watch live, re-attach to a
running run, or reopen a finished run.

## Decision

Treat a tool call as a first-class, identity-bearing entity in the run's
event stream. The run will emit a distinct kind of event for tool-call
activity that carries a stable id, the kind of action, a human-readable
summary, the current status, and (on failure) an error reason. These events
are recorded in the run's durable event history alongside every other event.

Both surfaces consume this shared model and render exactly one entry per
tool-call id, updating that entry in place as status changes and leaving it in
its final state once the call resolves.

## Alternatives Considered

### Alternative 1: Renderer-side line replacement

- **Description**: Keep tool calls as today's free-text log lines but thread
  the tool-call id through and teach each UI to overwrite the previous line
  for that id.
- **Pros**: Less plumbing; no new event model; smallest diff.
- **Cons**: No durable, structured representation, so re-attach and reopen of a
  finished run cannot faithfully reconstruct final states; the web reducer must
  parse text to recover identity; the two UIs can easily drift in behaviour.
- **Why rejected**: Fails the "full replay across CLI and web" requirement and
  bakes presentation concerns into the data, which is brittle.

### Alternative 2: Web-only now, CLI later

- **Description**: Ship the rich experience in the web UI first and defer the
  TUI to a later phase.
- **Pros**: Faster initial value where rich rendering is easiest.
- **Cons**: Contradicts the explicit "both surfaces" goal; leaves CLI users
  with today's noisy output indefinitely; risks the two surfaces never
  reaching parity.
- **Why rejected**: The user requirement is parity across CLI and web from the
  outset.

## Consequences

### Positive

- One clean, self-updating entry per tool call in both surfaces.
- Identical rendering live, on re-attach, and on reopen of finished runs.
- A single shared model means the CLI and web stay in lockstep.
- Room to add expandable detail (output/diffs) later without reworking the
  foundation.

### Negative

- More upfront work than a renderer-only patch: a new event shape plus changes
  in the daemon event history, the CLI, and the web client.

### Risks

- Older persisted runs predate the new event and will still render with legacy
  log lines — acceptable, since history is immutable and the change is
  forward-looking.
- Summaries must be derived from agent-provided data whose richness varies by
  IDE; mitigation is to fall back to the action title when details are absent.

## Implementation Notes

Implementation specifics (event field names, persistence format, reducer and
TUI changes) are deferred to the TechSpec. This ADR fixes only the product-
level decision that tool calls are a first-class, persisted, id-keyed event
consumed identically by both surfaces.
