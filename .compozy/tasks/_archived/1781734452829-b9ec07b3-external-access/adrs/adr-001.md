# ADR-001: Configurable bind address for external access

## Status

Accepted

## Date

2026-06-17

## Context

The workflow-runner daemon HTTP server is hardcoded to bind to `127.0.0.1:4517`
with a runtime assertion that aborts startup if the bind address deviates from
loopback. The CLI client communicates exclusively over a Unix domain socket, and
the security middleware enforces a `Host`-header allowlist accepting only
`127.0.0.1:<port>` and `localhost:<port>`.

Users want to access the web UI and API from other devices on their LAN and
potentially from the public internet behind their own reverse proxy. The
current architecture makes this impossible without source changes.

## Decision

Add a `--host` CLI flag and `WORKFLOW_RUNNER_HOST` environment variable to
the daemon to control the bind address (default `127.0.0.1`). Remove the
`assertLoopbackBind` runtime assertion and replace it with a warning on
non-loopback binds. Update the `Host`-header allowlist to accept any host value
when bound to `0.0.0.0`. No built-in TLS or authentication is added — users are
expected to bring their own reverse proxy and security layer for production
exposure.

## Alternatives Considered

### Alternative 1: Approach A + configurable origins

- **Description**: Same as the chosen approach, but also add a
  `--allowed-origins` flag / `WORKFLOW_RUNNER_ALLOWED_ORIGINS` env var to
  control the `Host`-header allowlist, and auto-enable CORS when bound to
  `0.0.0.0`.
- **Pros**: More flexible for LAN users who do not want a reverse proxy.
- **Cons**: Additional configuration surface, higher maintenance burden,
  encourages users to run without a reverse proxy in production.
- **Why rejected**: The user prefers the minimal approach and will handle
  their own network setup.

### Alternative 2: Approach A + LAN convenience (auto-detect IP)

- **Description**: Same as the chosen approach, but also detect the LAN IP on
  startup and print accessible URLs.
- **Pros**: Better UX for LAN users.
- **Cons**: Adds complexity for a cosmetic feature; users can determine their
  LAN IP themselves.
- **Why rejected**: The user prefers the minimal approach without extra UX
  polish.

## Consequences

### Positive

- Users can set `--host 0.0.0.0` to access the web UI and API from LAN
  devices without source modifications.
- Existing loopback-only behavior is preserved by default — no breaking
  change.
- Consistent with existing configuration patterns (`--api-port`,
  `WORKFLOW_RUNNER_API_PORT`).
- Minimal code change, low maintenance cost.

### Negative

- Binding to `0.0.0.0` exposes the daemon to the LAN without authentication
  or TLS. Users must understand the security implications and deploy a
  reverse proxy for internet exposure.
- The warning on non-loopback bind is advisory only — it may be ignored.

### Risks

- Users may bind to `0.0.0.0` and expose the daemon to the internet without
  a reverse proxy. Mitigation: the startup warning and documentation (users
  opted out of docs, so this is accepted).
- The `Host`-header allowlist change may introduce edge cases with multiple
  network interfaces. Mitigation: when binding to `0.0.0.0`, accept all
  `Host` values; when binding to a specific IP, continue enforcing the
  allowlist for that IP and `localhost`.

## Implementation Notes

- Add `--host` to the daemon CLI parser in `src/app/cli.ts` and route it to
  the daemon options.
- Add `WORKFLOW_RUNNER_HOST` env var with the same precedence rules as
  `WORKFLOW_RUNNER_API_PORT`: CLI flag > env var > default.
- Remove or bypass `assertLoopbackBind` in `src/infra/daemon/daemon.ts`.
- Update `Bun.serve()` in `daemon.ts` to use the configured hostname.
- Update `hostAllowlistMiddleware` and `isOriginAllowed` in
  `src/app/api/security.ts` to accept any host when the bind address is
  `0.0.0.0`.
- Default remains `127.0.0.1` — zero change for existing users.
