# ADR-001: Adopt shadcn across the whole app in V1 (sequenced, per-feature); defer command palette and live updates to V2

## Status

Accepted

## Date

2026-06-06

## Context

The `web/` workspace has shadcn/ui configured (new-york style, zinc base, CSS-variable theming, `cn()` present) but only three primitives exist (`button`, `input`, `label`). Tables, status banners, forms, and the app shell are hand-rolled Tailwind. The stated goal — "improve web design to actually use shadcn, and add the best things to the dashboard" — carries an unbounded scope risk: literally adopting shadcn across every feature (workflows editor, start-run form, run view) becomes a multi-week rewrite that holds the entire Vitest suite hostage to simultaneous DOM churn.

The web UI is a secondary control surface for a solo-developer, local-first tool that also ships a CLI and a rich TUI. Its distinct value versus those surfaces is **glanceable state** (what is running / failing right now) and **workflow authoring** — not command dispatch, which the CLI already does well. A five-advisor council (pragmatic-engineer, architect-advisor, product-mind, devils-advocate, the-thinker) debated where to draw the V1 line and recommended bounding the migration to shell + dashboard. **The decision owner overrode that recommendation**: full-app shadcn adoption is in V1 scope. This ADR records the accepted decision and folds the council's rewrite-trap concern in as a sequencing discipline rather than a scope cut.

## Decision

V1 adopts shadcn/ui across the **entire** web app, plus the dashboard command-center payload. It is executed as a sequence of small, independently-shippable PRs — never a single big-bang rewrite:

1. **Status design tokens + a shared `<StatusBadge>`** — extract semantic status color pairs into `:root`/`.dark` and a single reusable badge component. Done **first**, quarantining the one token-coupled, volatile piece. (PR 1)
2. **App shell** — replace the hand-rolled `AppShell` sidebar with the shadcn `sidebar-07` pattern (`SidebarProvider`/`SidebarInset`), preserving existing nav routes, `DaemonStatus`, and `CwdSwitcher` (and its tested `aria-pressed`/label contracts). (PR 2)
3. **RunsTable migration** to shadcn `Table` primitives, carrying every `data-testid` and ARIA role forward. (PR 3)
4. **Status summary cards** (running / completed-success / failed / crashed / aborted) derived client-side from the existing `listRuns` 2s poll, **click-to-filter** the runs list. (PR 4)
5. **Remaining features migrated to shadcn** — workflows list, workflow editor (+ step/edges/agent-model fields), start-run form, run view (banners, transcript, controls, input box) — each as its own bounded PR. (PRs 5+)
6. **Light/dark mode selector**, skeletons, and action-oriented empty states. (PR 6)

Each PR lands green before the next. The **⌘K command palette** and **live (SSE) dashboard updates** are explicitly **deferred to V2**. The 2s poll is retained in V1 as deliberate, logged debt.

## Alternatives Considered

### Alternative 1: Bound the migration to shell + dashboard only (council recommendation)

- **Description**: Migrate only the app shell and dashboard to shadcn in V1; leave workflows editor, start-run form, and run view hand-rolled until a later milestone.
- **Pros**: Smallest blast radius; ships in days; test suite barely perturbed.
- **Cons**: Leaves a visible half-migrated seam (shadcn shell next to hand-rolled features); full consistency deferred indefinitely with risk of never finishing.
- **Why not chosen**: This was the council's unanimous recommendation, but the decision owner prioritized full visual/structural consistency and chose to migrate the whole app. The council's risk (rewrite trap) is mitigated by sequencing (per-feature PRs) rather than by cutting scope.

### Alternative 2: Command-surface ("cockpit") first — center V1 on the ⌘K palette

- **Description**: Treat the web UI as an active command surface; build the ⌘K palette (mirroring CLI verbs) as the V1 centerpiece, with status as supporting context.
- **Pros**: A genuinely distinctive feature; CLI verbs map 1:1 to palette actions.
- **Cons**: Bets V1 on an unproven behavior (the solo dev preferring the browser over the terminal they already live in); adds a new subsystem (global key intercept, command registry synced to run state) with zero existing test coverage.
- **Why rejected**: Product-mind + devils-advocate: invest in the observation layer that earns daily opens *first*; add the palette once the web UI proves it gets used. Deferred to V2, not discarded.

### Alternative 3: Live SSE dashboard updates in V1

- **Description**: Replace/augment the 2s poll with a global runs-list SSE feed so status changes reflect instantly.
- **Pros**: Eliminates the staleness gap versus the real-time TUI; reinforces the "monitoring" feel.
- **Cons**: The existing WebSocket feed is per-run `attach` (`/runs/{id}/attach`), NOT a global list feed — so this is new plumbing across three layers (daemon broadcast, client fan-out, reconnect/backfill), introducing a new failure-mode class.
- **Why rejected**: Pragmatic + architect held firm: multi-day infra to shave 2s of latency. Product-mind partially conceded (the "reuse existing feed" premise was factually wrong) but logged dissent that a stale web UI erodes trust. Deferred to V2 as a properly-scoped status-diff endpoint.

## Consequences

### Positive

- Full visual and structural consistency: one component system across the entire app, no half-migrated seam.
- Establishes a reusable shadcn component layer + status token system that lowers the cost of every future component, including the V2 mission-control view.
- Dashboard delivers the requested glanceable triage (cards + live-ish list) with near-zero data cost.
- Click-to-filter cards give the run cards real interaction affordance now, cheaply settling the "sealed display vs. action-ready" design question without committing to the palette.

### Negative

- Larger V1 than the council advised — weeks rather than days; more total migration surface and test churn.
- 2s poll staleness persists; web UI lags the TUI's real-time view by up to ~2s.
- Form-heavy features (workflow editor, start-run) carry the most migration risk and effort (react-hook-form + zod wiring into shadcn `Form`/`Select`).

### Risks

- **Rewrite-trap / never-finishing** (the council's central concern). *Mitigation*: strict per-feature PR sequencing, each landing green; the migration order is fixed (tokens → shell → table → cards → remaining features → polish); no big-bang branch.
- **Silent test breakage** across the 19-file suite — assertions on `run-row-${id}`, `getByRole('table')`, `aria-pressed`, form labels (`getByLabelText`), and many `data-testid`s. *Mitigation*: extract `<StatusBadge>` first; carry all `data-testid`s and roles forward; deliberate selector audit per PR; suite is the regression gate.
- **`sidebar-07` and shadcn `Form`/`Select` fighting existing router/query/store/react-hook-form wiring.** *Mitigation*: thin structural swaps; do not refactor component internals (`CwdSwitcher`, `DaemonStatus`, form logic) in the same PR as the shadcn shell swap.

## Implementation Notes

Sequencing within V1: (1) status tokens + `<StatusBadge>` → (2) app shell (`sidebar-07`) → (3) RunsTable → shadcn `Table` (selector audit) → (4) summary cards with click-to-filter → (5) remaining features migrated one PR each (workflows list, workflow editor + fields, start-run form, run view) → (6) light/dark selector, skeletons, empty states. Each step lands green before the next; no combined big-bang PR.
