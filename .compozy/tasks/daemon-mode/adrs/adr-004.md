# ADR-004: JSON-RPC 2.0 over NDJSON for the Daemon Protocol

## Status

Accepted

## Date

2026-05-25

## Context

The daemon and CLI client communicate over a Unix domain socket. The protocol must support: (1) request/response exchanges for control commands (`start`, `attach`, `ps`, etc.); (2) server-pushed events for streaming a run's event log to an attached TUI; (3) graceful error semantics; (4) future evolution as commands are added or refined.

Three envelope choices were considered: a full JSON-RPC 2.0 wire format over newline-delimited JSON, a bespoke `{kind, data}` envelope, and length-prefixed JSON frames.

JSON-RPC 2.0 is a well-specified standard (request, response, notification, error all explicitly defined). NDJSON framing is the simplest robust delimiter for streaming JSON and is trivially debuggable with `nc -U` or `socat`. The combination is the same shape used by Language Server Protocol (LSP), Agent Client Protocol (which the project already depends on), Debug Adapter Protocol, and a long tradition of editor tooling — so the ergonomics, error semantics, and idioms are well understood.

A bespoke envelope is smaller but reinvents id correlation, notification semantics, and error envelopes; over time it accumulates the same complexity but ad hoc. Length-prefixed framing solves a problem (handling embedded newlines in JSON strings) that NDJSON's natural newline boundaries do not actually have, at the cost of making the wire binary at the framing layer.

The project already imports `@agentclientprotocol/sdk` which uses NDJSON internally (`ndJsonStream`), so the toolchain is familiar.

## Decision

The daemon ↔ CLI protocol is **JSON-RPC 2.0** with messages framed by NDJSON (one JSON object per line, `\n` terminator, no embedded raw newlines in objects). The daemon implements the JSON-RPC server side; the CLI client implements the JSON-RPC client side.

Method namespace: dotted names by capability (`run.start`, `run.ps`, `run.attach`, `run.send`, `run.retryStep`, `run.stop`, `daemon.doctor`, `daemon.shutdown`). Server-pushed events use notifications (JSON-RPC messages with no `id`) on a method namespace `event.run.<eventKind>` correlated to the subscribed `runId` in `params`.

A small in-house JSON-RPC implementation lives under `src/infra/daemon/rpc/`; no third-party JSON-RPC library is added. The implementation surface is bounded (~150 lines) and the protocol is stable.

## Alternatives Considered

### Alternative 1: Bespoke `{kind, data}` envelope

- **Description**: Each message has a `kind` discriminator (`request`, `response`, `event`) and a `data` payload. Request/response correlation by client-supplied `requestId`.
- **Pros**: Minimal code; no spec to follow.
- **Cons**: Reinvents error semantics, notification vs response, id correlation, and version evolution; the implementation will end up being a worse JSON-RPC over time.
- **Why rejected**: The spec is the value, not the bytes.

### Alternative 2: Length-prefixed JSON frames

- **Description**: 4-byte big-endian length followed by the JSON payload.
- **Pros**: Tolerant of embedded newlines without escaping; explicit framing.
- **Cons**: NDJSON has the same robustness for JSON payloads (which never contain raw `\n` in normal serialization) without binary framing; debuggability with `nc`/`socat` drops sharply once you can't see message boundaries.
- **Why rejected**: NDJSON gives the practical benefits without the cost.

### Alternative 3: A third-party JSON-RPC library

- **Description**: Pull in a published `json-rpc` package.
- **Pros**: Spec compliance out of the box.
- **Cons**: Most published Node JSON-RPC libraries are over-engineered (transport abstractions, middleware) or under-maintained; the bounded ~150 LOC version we need has no operational benefit from a dep.
- **Why rejected**: YAGNI; the protocol's request/response/notification surface is small enough to own.

## Consequences

### Positive

- Debuggable from any shell with `socat - UNIX-CONNECT:<sock>` then typing JSON-RPC requests by hand.
- Server-pushed events fit cleanly into JSON-RPC notifications; no separate "subscription" protocol invented.
- Error responses use the spec's `{code, message, data}` shape, which is familiar to anyone who has integrated LSP or ACP.
- Method namespacing (`run.*`, `daemon.*`, `event.*`) leaves room for future surface growth without breaking changes.

### Negative

- We hand-roll a small JSON-RPC implementation. Maintenance burden is real but bounded.
- JSON-RPC's batch-request support is in the spec but unused by us; the implementation explicitly does not support batching to keep code small. (We document this as a known limitation, not a defect.)

### Risks

- **Risk**: A future method name conflicts with the namespace convention. **Mitigation**: All current methods follow `<scope>.<action>`; this is enforced by the request dispatcher's lookup table.
- **Risk**: A notification is missed by the client because the socket buffer overflowed mid-burst. **Mitigation**: The daemon uses backpressure-aware writes (await drain on the socket); if a subscriber falls behind, the daemon closes that subscription with an error notification so the client can re-attach.

## Implementation Notes

- Message types: `Request { jsonrpc: "2.0", id, method, params? }`, `Response { jsonrpc: "2.0", id, result? | error? }`, `Notification { jsonrpc: "2.0", method, params? }`.
- IDs are positive integers, monotonically allocated per connection.
- Each connection is a single NDJSON-framed bidirectional stream; multiple in-flight requests on one connection are correlated by `id`.
- Server-pushed events on a connection are scoped to that connection's subscriptions; closing the connection drops subscriptions.
