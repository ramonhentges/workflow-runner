# ADR-003: Dedicated `initialPrompt` field on the run snapshot

## Status

Accepted

## Date

2026-06-12

## Context

The PRD requires the prompt a run was started with to be visible in the run view
after the fact (PRD Core Feature #3). The run already persists a per-step
`kickoffPrompts: Record<StepId, string>` on its `RunSnapshot`, and the entry
step's kickoff contains the framed prompt text. However, that record:

- mixes the user's prompt with mode instructions and the step description, so the
  raw user text cannot be shown cleanly without parsing, and
- is not currently surfaced in the run view (which only renders branch/worktree).

We must decide whether to reuse the existing `kickoffPrompts` data or add a
dedicated field.

## Decision

Add an optional `initialPrompt?: string` field to `RunSnapshot` (and the derived
`RunDetail`/`RunSummary` API schema where the run view reads it), mirroring the
existing optional `branch` field exactly:

- Set at `Run.create` from the value threaded through `startRun`.
- Serialized in `snapshot()` only when present (omitted otherwise), so existing
  persisted runs and no-prompt runs are unaffected.
- Persisted by the run store like every other snapshot field.
- Rendered as its own labeled section in `RunView`, alongside the existing
  isolation (branch) display. Kept out of the compact `ps` list (PRD Non-Goal).

## Alternatives Considered

### Alternative 1: Derive the prompt from the entry-step `kickoffPrompts`

- **Description**: No new field; extract the prompt from the entry step's recorded
  kickoff text for display.
- **Pros**: No schema change.
- **Cons**: The stored kickoff blends user text with mode instructions and the
  description; display code would have to parse framed text, coupling the UI to the
  exact kickoff wording. Fragile when the wording changes (see ADR-002).
- **Why rejected**: Couples presentation to internal kickoff formatting; a clean
  dedicated field is cheaper to maintain.

### Alternative 2: Persist only in the event log, not the snapshot

- **Description**: Emit the prompt as a log event rather than snapshot state.
- **Pros**: Avoids a snapshot field.
- **Cons**: Run view would have to scan the event backlog to reconstruct a single
  start-time fact; lost when the log is truncated.
- **Why rejected**: The prompt is durable run metadata, identical in shape to
  `branch`; the snapshot is its natural home.

## Consequences

### Positive

- Raw user prompt is available for clean display without parsing.
- Reuses the proven `branch` optional-field pattern across snapshot, store, and
  API schema.
- Backward compatible: absent on old/no-prompt runs.

### Negative

- One more optional field on the snapshot and the API schema to maintain.

### Risks

- Long prompts could bloat the run view — mitigated by treating it as ordinary
  metadata in its own section and excluding it from compact listings.

## Implementation Notes

- `RunSnapshot` (`src/domain/run.ts`), `RunDetailSchema`/`RunSummarySchema`
  (`src/app/api/schema.ts`), and `RunView.tsx` are the touchpoints.
- Follow the conditional-serialization style already used for `branch`/`cwd`.
