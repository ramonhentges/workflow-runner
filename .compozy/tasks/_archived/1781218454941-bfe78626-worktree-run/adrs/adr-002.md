# ADR-002: Git worktree operations via simple-git behind an injectable adapter

## Status

Accepted

## Date

2026-06-11

## Context

Isolated runs (ADR-001) require creating git worktrees, detecting whether a directory is a git repository, resolving the repository root, and checking branch existence. `RunManager.startRun` is the orchestration point. `RunManager` is unit-tested with fakes injected via `RunManagerOptions` (e.g. `createMcpServer`, `generateId`, `generateSlug`), and touching real git in those tests would be slow and environment-dependent.

The project currently shells out to `node:child_process` to spawn agent subprocesses and has no git dependency. `isomorphic-git` (pure JS) does not support `git worktree`, so it cannot satisfy the requirement.

## Decision

Add **`simple-git`** as a dependency and wrap it in a single infra adapter, `GitWorktrees`, exposing only the operations the feature needs: resolve repository root (and thereby detect a non-repo), check branch existence, and add a worktree. Inject the adapter into `RunManager` through `RunManagerOptions`, mirroring the existing dependency-injection pattern. Unit tests pass a fake `GitWorktrees`; integration tests construct real temporary git repositories.

Per the project's port rule (a port interface is warranted only with two or more implementations), `GitWorktrees` is a single interface with one real adapter plus a test fake — the fake is a second implementation, so the seam is justified.

## Alternatives Considered

### Alternative 1: simple-git used directly inside RunManager

- **Description**: Call `simple-git` inline in `startRun`, no adapter.
- **Pros**: Less indirection.
- **Cons**: `RunManager` unit tests would invoke real git; harder to simulate branch-in-use and non-repo cases.
- **Why rejected**: Breaks the established injectable-dependency testing pattern.

### Alternative 2: Shell out to the git CLI directly (node:child_process)

- **Description**: Spawn `git` and parse output, no library.
- **Pros**: Zero new dependencies; matches how agents are spawned.
- **Cons**: Hand-rolled argument handling and output parsing for repo detection, branch checks, and worktree add.
- **Why rejected**: The user chose a typed library for ergonomics and fewer parsing bugs.

### Alternative 3: isomorphic-git

- **Description**: Pure-JS git implementation.
- **Pros**: No dependency on an installed git binary.
- **Cons**: Does not support `git worktree`.
- **Why rejected**: Cannot perform the core operation.

## Consequences

### Positive

- Worktree logic is isolated behind a small, mockable seam.
- `RunManager` tests stay fast and deterministic with a fake adapter.
- Behavior tracks the user's installed git (simple-git wraps the CLI).

### Negative

- Adds a third-party dependency and a transitive reliance on the git binary being installed.

### Risks

- simple-git surfaces git errors as exceptions with provider-specific messages; the adapter must translate branch-in-use / path-exists into stable, mapped error codes. Mitigation: the adapter normalizes failures; `RunManager` maps them to RPC error codes.

## Implementation Notes

Adapter operations (final signatures in the TechSpec): `resolveRepoRoot(dir) → string | null`, `branchExists(repoRoot, branch) → boolean`, `addWorktree({ repoRoot, worktreePath, branch, createBranch })`.
