# ADR-002: In-process HTTP MCP server for the handoff and finish tools

## Status

Accepted

## Date

2026-05-22

## Context

Each workflow step must expose two tools to the running agent — `handoff`
(choose the next step) and `finish` (end the workflow). ACP does not let a client
define custom tools directly; the only mechanism is an MCP server declared in the
`mcpServers` array of `session/new`. The runner therefore must host an MCP server.

The hard requirement is that, when the agent calls one of these tools, the
**runner** must learn the decision and act on it (tear down the session, advance
to the next step, or finish). The transport choice determines how that signal
reaches the runner.

ACP supports three MCP transports: stdio (all agents must support it), HTTP, and
SSE (deprecated). HTTP and SSE are gated behind `agentCapabilities.mcpCapabilities`
reported at `initialize`. opencode natively supports remote (HTTP) MCP servers,
so it advertises `mcpCapabilities.http: true`.

## Decision

Run a single **in-process HTTP MCP server** inside the runner process for the
entire workflow run. It listens on `127.0.0.1` on an ephemeral port and exposes
the `handoff` and `finish` tools. Every step's session is created with
`mcpServers: [{ type: "http", name: "workflow", url, headers: [] }]` pointing at
this server.

Because the runner hosts the server in-process, the tool handlers are plain
closures over runner state. `handoff` validates the requested `next_step` against
the current step's edges and resolves a promise the runner's orchestration loop
is awaiting; `finish` resolves the same loop with a finish outcome. No separate
process and no inter-process channel are needed. The runner verifies
`mcpCapabilities.http` at `initialize` and fails fast with a clear message if it
is absent.

## Alternatives Considered

### Alternative 1: Stdio MCP subprocess with an IPC back-channel

- **Description**: A separate MCP server process (stdio, the universally
  supported transport) is spawned by opencode. It relays each tool call back to
  the runner over a local socket whose address is passed via environment
  variables.
- **Pros**: Works even if the agent does not support HTTP MCP.
- **Cons**: Adds a second process and a hand-written IPC protocol; the runner
  must run a socket listener and correlate requests; more failure modes.
- **Why rejected**: opencode supports HTTP MCP, so the IPC layer would
  reimplement HTTP for no benefit.

### Alternative 2: Stdio MCP server, decision read from session updates

- **Description**: A stdio MCP server whose tools simply return success; the
  runner reads the `next_step`/`message` arguments from the `rawInput` field of
  `tool_call` session-update notifications.
- **Pros**: No IPC and no separate decision channel.
- **Cons**: Depends on opencode reliably populating `rawInput` for MCP tool
  calls; couples control flow to an observability stream; turn-completion timing
  is harder to reason about.
- **Why rejected**: Control flow should not depend on a notification stream
  intended for display; the HTTP handler gives a direct, synchronous signal.

## Consequences

### Positive

- Tool handlers directly manipulate runner state — no IPC, no serialization of
  the decision, no second process to supervise.
- One MCP server is reused across every step's session for the whole run.
- `handoff` can validate `next_step` against the live current-step edges at call
  time, since the handler closes over runner state.

### Negative

- The runner now also runs an HTTP server, adding a small surface (port binding,
  shutdown) to manage.
- The design depends on `mcpCapabilities.http`; an agent without it is
  unsupported.

### Risks

- Port binding could fail or collide. Mitigation: bind to an ephemeral port on
  `127.0.0.1` and read the assigned port back before creating any session.
- A future non-opencode agent might lack HTTP MCP support. Mitigation: the
  capability is checked at `initialize` and the runner exits with a clear
  message; a stdio fallback can be added later if needed.

## Implementation Notes

The MCP server is built with `@modelcontextprotocol/sdk` using its Streamable
HTTP transport. Steps run strictly one at a time, so a single shared server with
handlers that reference "the current step" is sufficient — no per-session
routing. The server starts once before the first step and is closed during
runner cleanup.
