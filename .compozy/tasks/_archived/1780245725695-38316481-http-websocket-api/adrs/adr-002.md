# ADR-002: V1 surface expansion — retry-step, health, and explicit spawn path

## Status

Accepted

## Date

2026-05-29

## Context

ADR-001 set the V1 shape for the HTTP+WebSocket API: a thin set of adapters over a
transport-agnostic application-service seam (Hono + Zod), with a deliberately minimal
endpoint slice (`GET /runs`, `GET /runs/:id`, `POST /runs`, `POST /runs/:id/stop`,
`WS /runs/:id/attach`). Retry-step, daemon health/doctor, and `ps all=true` were explicitly
deferred "until a real consumer surfaces a need."

During PRD brainstorming the primary V1 consumer was confirmed to be a **future web-UI
developer** building a dashboard against the API contract — not just the maintainer's own
scripts. With that consumer in view, two gaps in the ADR-001 slice became load-bearing:

1. A dashboard that shows a failed run needs a first-class way to **recover** it. Today the
   only recovery verb is `retry-step`, exposed over the CLI/JSON-RPC but excluded from the
   API slice. Without it, a UI can observe failure but not act on it — forcing the user back
   to a terminal and breaking the "match TUI capabilities" goal.
2. A dashboard needs a cheap, unauthenticated **health/liveness signal** to decide whether
   the daemon is reachable before issuing control verbs, and to render a connection state.
   The existing `doctor` capability covers this but was deferred.

Separately, the CLI starts a run by reading a workflow JSON path and spawning the runner in
the shell's current working directory — an implicit parameter. An HTTP consumer has no
ambient shell, so the working directory the agent runs in must become an **explicit input**
to `POST /runs`. This was not specified in ADR-001 (which listed only `workflowPath`).

## Decision

Expand the locked V1 API surface, still within the Approach A (shared application-service
seam) architecture from ADR-001:

- **Add `POST /runs/:id/retry-step`** to V1 — retries the failing step of a run, reachable
  over both HTTP and the existing JSON-RPC transport via the shared service.
- **Add `GET /health`** to V1 — an unauthenticated daemon liveness/health snapshot suitable
  for a dashboard to poll before issuing control verbs.
- **`POST /runs` takes two explicit paths** — the workflow file path *and* the working
  directory ("spawn path") in which the runner is launched. The application-service operation
  and both transports carry this parameter; the CLI continues to default the spawn path to
  its current working directory for backward compatibility.

`ps all=true`, SSE, replay/fork, AsyncAPI, and auth remain deferred per ADR-001.

## Alternatives Considered

### Alternative 1: Keep ADR-001's minimal slice; add retry-step and health only when the UI is built

- **Description**: Ship list/detail/start/stop/attach only; let the future UI surface the
  need for recovery and health before adding endpoints.
- **Pros**: Smallest V1 surface; strictly honors the "no endpoint without a consumer" rule;
  least up-front work.
- **Cons**: The consumer is already known to be a UI dev, and a recovery action plus a
  liveness check are table stakes for any dashboard — deferring them guarantees a fast-follow
  and a contract bump. Observing a failure a UI cannot act on violates the TUI-parity goal.
- **Why rejected**: The "consumer that doesn't exist yet" rationale for deferral no longer
  holds once the consumer and its baseline needs are confirmed. Both verbs already exist in
  the domain; exposing them at the same seam is near-zero marginal cost.

### Alternative 2: Default the spawn path to the daemon's working directory (no explicit parameter)

- **Description**: `POST /runs` accepts only `workflowPath`; the runner always spawns in the
  daemon's cwd.
- **Pros**: Matches `POST /runs` body shape in ADR-001 exactly; simplest request schema.
- **Cons**: A daemon is a long-lived background process whose cwd is effectively arbitrary;
  agents would run against the wrong project tree. A UI driving runs across multiple project
  directories could not express where work should happen.
- **Why rejected**: Makes the API unusable for its primary purpose (running workflows against
  a chosen project). The working directory is a genuine product input, not an implementation
  detail.

## Consequences

### Positive

- A future dashboard can observe, control, **recover**, and health-check runs without ever
  dropping to a terminal — the TUI-parity goal is met for the verbs that matter to a UI.
- The spawn-path parameter makes the API usable across multiple project directories, which a
  single-cwd CLI never had to express.
- Because everything routes through the shared service (ADR-001), each added verb is exposed
  to JSON-RPC and HTTP at once, with one Zod DTO and one conformance test.

### Negative

- Slightly larger V1 surface than ADR-001 (two more endpoints, one more start parameter) →
  more schemas, more route handlers, more tests.
- The explicit spawn path is a new control input that, combined with localhost-no-auth, lets
  any permitted local caller launch an agent in an arbitrary directory — raising the stakes
  on the ADR-001 loopback/Origin/Host security baseline.

### Risks

| Risk | Mitigation |
|---|---|
| Spawn-path widens the confused-deputy blast radius for DNS-rebinding/CSRF (arbitrary-dir code execution) | Inherit ADR-001's non-negotiable baseline: IPv4 loopback bind + bind assertion, `Host` allowlist on HTTP, `Origin` allowlist on WS, DNS-rebinding falsification test in CI. |
| `GET /health` leaks run/daemon internals to an unauthenticated caller | Health payload is a minimal liveness/version snapshot, not run contents; same loopback baseline applies. |
| Retry-step exposed over HTTP races with an in-flight step or stale attach client | Route through the shared service which already guards step ownership (per-step `StepToken`); re-verify against the WS attach lifecycle. |

## Implementation Notes

- Retry-step and health route handlers stay thin and delegate to the shared application
  service alongside the other verbs (per ADR-001 Approach A).
- The application-service `startRun` operation and its JSON-RPC + HTTP adapters gain the
  spawn-path parameter; the CLI populates it from `process.cwd()`.
