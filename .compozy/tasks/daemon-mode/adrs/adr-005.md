# ADR-005: Code Layout — Domain Run + Infra Adapters + App CLI Dispatcher

## Status

Accepted

## Date

2026-05-25

## Context

The project follows hexagonal architecture (`CLAUDE.md`): `domain` is I/O-free business logic; `app` wires; `infra` adapts. Daemon mode adds substantial new code — a `Run` aggregate, a `RunManager`, a UDS server, a JSON-RPC dispatcher, an event-log writer, a CLI client, and several new subcommands. The question is where this code lives without breaking the existing seams.

The existing layout has clear ownership:

- `src/domain/workflow.ts`, `runner.ts`, `outcome.ts`, `ids.ts` — pure logic.
- `src/app/main.ts`, `cli.ts` — wiring of one workflow run.
- `src/infra/mcp/`, `acp/`, `tui/` — I/O adapters.

A `Run` aggregate has clear domain status: it holds status (`running`, `completed`, `failed`, `crashed`, `aborted`), eligibility rules (`retry-step` only on `crashed`/`failed`/`aborted`), and id/slug identity. Its state transitions are pure functions over events. It is not coupled to disk, socket, or subprocess. This is squarely domain.

The daemon process (UDS server, JSON-RPC handlers, event-log writer, run-directory discovery) is I/O. It belongs in `infra`. The CLI client (which connects to the daemon over UDS, sends requests, prints output) is also I/O — it belongs in `infra` as well.

The `app` layer becomes a subcommand dispatcher that parses argv, decides whether to run the daemon foreground or invoke a client command, and wires together the relevant infra pieces.

## Decision

The new code is organized as follows:

- `src/domain/run.ts` — `Run` aggregate: `id`, `slug`, `workflowPath`, `status`, `currentStepId`, `visitedStepIds`, `startedAt`, `endedAt`, `kickoffPrompts: Map<StepId, string>`. Pure state-transition methods (`markRunning`, `markCrashed`, `markCompleted`, `markFailed`, `markAborted`, `eligibleForRetry()`).
- `src/domain/run-id.ts` — Run-id and slug generation (pure functions; deterministic given a random byte source which is injected for testing).
- `src/infra/daemon/` — Daemon implementation:
  - `daemon.ts` — Daemon entry, socket binding, lockfile, lifecycle.
  - `run-manager.ts` — Owns the set of active `Run`s, their `McpServer` instances, their `Runner`s, their per-run state directories.
  - `event-log.ts` — Append-only `events.jsonl` writer with ring-buffer cache for replay.
  - `run-store.ts` — Read/write of `meta.json`; discovery of run directories on startup.
  - `rpc/` — JSON-RPC server (request dispatch, notification fan-out, error envelopes).
  - `handlers/` — One file per JSON-RPC method (`run-start.ts`, `run-attach.ts`, etc.) for grep-ability.
- `src/infra/client/` — CLI client implementation:
  - `client.ts` — UDS connection, JSON-RPC client, auto-spawn-daemon logic.
  - `format.ts` — `ps` / `doctor` output formatting (humanized durations, marker glyphs).
- `src/infra/tui/` — TUI gets a new `attach-to-daemon.ts` that hosts the existing `Tui` against a UDS subscription instead of an in-process `Runner`. Existing `tui.ts` is refactored to depend on an observable event source rather than a `Runner` directly.
- `src/app/main.ts` — Subcommand dispatcher only. Parses argv, dispatches to `runDaemon()` or `runClientCommand()` from the relevant infra modules.
- `src/app/commands/` — One thin file per subcommand to wire CLI parsing → client call → exit code. Kept here (not in `infra/client/`) because these are wiring, not adapters.

Tests live next to the code they cover, matching the existing `*.test.ts` convention. The new `src/infra/daemon/__tests__/integration/` directory holds the integration tests against a real daemon over a temp socket with a fake agent factory.

## Alternatives Considered

### Alternative 1: Flat new `daemon/` and `cli/` packages alongside `app/`

- **Description**: Treat daemon and CLI as new top-level layers; `src/daemon/`, `src/cli/`.
- **Pros**: Easier to see "here is the daemon, here is the client" at a glance.
- **Cons**: Breaks the hexagonal pattern the rest of the code follows; new contributors face two architectural conventions; over time these become legacy layers that drift.
- **Why rejected**: Hexagonal seams already accommodate the new code cleanly; no benefit to inventing a parallel structure.

### Alternative 2: Everything in `infra/daemon/`, including a Run "model"

- **Description**: Put `Run` in `src/infra/daemon/run.ts` because Run lifecycle is tightly coupled to persistence.
- **Pros**: One place to look for everything daemon-related.
- **Cons**: `Run`'s status transitions, retry eligibility, and id/slug identity are pure business logic with no I/O; pushing them into infra hides domain logic behind an I/O concern, which is exactly what hexagonal architecture rules against; testing pure Run logic becomes harder because it lives next to I/O.
- **Why rejected**: `Run` is genuinely domain; misplacing it would echo for every future refactor.

## Consequences

### Positive

- New code obeys the existing rule that `domain` has zero imports from `infra`. The `Run` aggregate is unit-testable in pure isolation.
- Test placement matches existing convention; integration tests have an obvious home.
- `app/main.ts` shrinks to a small dispatcher; subcommand wiring is one file each, easy to skim.
- The TUI refactor (depend on an event source, not a `Runner`) makes it equally usable in foreground tests and against a real daemon, increasing reuse.

### Negative

- `src/infra/daemon/handlers/` will have ~10 small files (one per JSON-RPC method). The directory will look busy, but each file stays under ~50 lines and the per-file structure pays for itself in `git blame` and grep.
- The TUI refactor touches existing code; existing tests must be updated to use the new abstraction.

### Risks

- **Risk**: Domain `Run` becomes a dumping ground as features grow ("Run also handles persistence", "Run also tracks subscribers"). **Mitigation**: Code-review rule: any I/O import inside `domain/run.ts` is a red flag; persistence and subscribers live in `infra/daemon/`.
- **Risk**: The `infra/client/` and `infra/daemon/` directories drift apart (the client expects one method shape, the daemon implements another). **Mitigation**: Both sides import a shared `src/infra/daemon/protocol.ts` file that declares the JSON-RPC method names, parameter types, and result types; type errors catch divergence at compile time.

## Implementation Notes

The shared `src/infra/daemon/protocol.ts` is the single source of truth for the protocol. Both daemon handlers and CLI client import from it. It lives in `infra/daemon/` not `domain/` because it describes a wire format (an I/O concern), and the CLI client depending on a sibling-infra file is acceptable (it's not depending on domain → infra).
