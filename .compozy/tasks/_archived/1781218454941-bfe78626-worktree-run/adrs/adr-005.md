# ADR-005: Reuse an existing worktree for a branch instead of erroring

## Status

Accepted

## Date

2026-06-11

## Context

ADR-001 and the initial TechSpec draft treated "the branch is already checked out by another worktree" as a hard failure (`WORKTREE_CONFLICT`). In review, the user clarified the intended workflow: starting an isolated run on a branch that already has a worktree is a legitimate case — the user is *extending* work already begun there and wants the run to execute inside the existing worktree, not be rejected.

This refines the PRD's *Clear failure on invalid isolation request* feature: an already-checked-out branch is no longer an error.

## Decision

When provisioning an isolated run, first look up whether `branch` already has a registered worktree in the repository (via `git worktree list`). If it does, **reuse that worktree's path** as the run's `worktreePath` and skip worktree creation. Otherwise, create a new worktree adjacent to the repo (ADR-003), creating the branch off HEAD if it does not exist.

A genuine conflict remains only when the *computed new* worktree path is occupied by a directory that is **not** a worktree for this branch; that maps to `WORKTREE_CONFLICT`. A non-git directory still maps to `NOT_A_GIT_REPO`.

Consequence for concurrency: two isolated runs on the **same** branch now share the same worktree directory rather than the second being rejected. This is the user's explicit intent (extending work); callers who need isolation between concurrent runs use **distinct** branches (PRD: *High-Level Technical Constraints — distinct branch names*).

## Alternatives Considered

### Alternative 1: Error on already-checked-out branch (original design)

- **Description**: Reject with `WORKTREE_CONFLICT` when the branch already has a worktree.
- **Pros**: Guarantees no two runs ever share a directory.
- **Cons**: Blocks the legitimate "continue/extend work on this branch" flow the user wants.
- **Why rejected**: Contradicts the intended workflow.

### Alternative 2: Always create a fresh, uniquely-named worktree per run

- **Description**: Never reuse; suffix the path to avoid collisions.
- **Pros**: Always isolated.
- **Cons**: Cannot resume work in the same directory; proliferates worktrees; conflicts with checking out an existing branch.
- **Why rejected**: Defeats the resume/extend use case.

## Consequences

### Positive

- Restarting or layering a run on an in-progress branch "just works" in the existing worktree.
- Fewer error paths; the common resume case is frictionless.

### Negative

- Two concurrent runs on the same branch share a directory and can clobber each other — the very problem isolation solves. This is now the caller's responsibility to avoid by using distinct branches.

### Risks

- A user unintentionally reuses a branch and gets shared-directory behavior. Mitigation: surface the resolved `worktreePath` so reuse is visible; document that concurrent isolation requires distinct branches.

## Implementation Notes

Adds `findWorktreeForBranch(repoRoot, branch) → string | null` to the `GitWorktrees` adapter (parses `git worktree list --porcelain`). `RunManager.startRun` consults it before computing a new path.
