# ADR-001: Unified optional initial prompt across all run-start surfaces

## Status

Accepted

## Date

2026-06-12

## Context

Today a run is started from three surfaces — the CLI `start` command, the web
Start Run form, and the web workflow-list run dialog — and none of them lets the
user provide a per-run task message. The first step's agent receives only the
workflow's static `description`, so the same workflow always begins the same way.
Users who want to direct a run ("work on the auth bug", "review PR #42") have no
way to do so without editing the workflow file.

The runner already accepts an optional inbound message for the entry step
(`runner.run(startStepId, startInboundMessage)`), but only the retry/resume path
supplies one; the `run.start` contract does not. A recently shipped `branch`
field demonstrates the established pattern for threading an optional field from
all three surfaces through to the start contract.

We must decide the scope and shape of the feature: which surfaces get it, whether
the prompt is persisted and shown after start, and whether to ship it as one unit
or in phases.

## Decision

Add a single **optional** "initial prompt" field, delivered across all three
start surfaces in one release, mirroring the existing `branch` field pattern:

- CLI `start` accepts the prompt via a flag (inline text, plus stdin/file for
  longer prompts), consistent with the `send <run-id> -` convention.
- The web Start Run form and the workflow-list run dialog each expose an optional
  multi-line prompt field.
- The prompt is handed to the first step's agent under a distinct
  "user request for this run" framing — semantically separate from the inter-step
  "Context from previous step" handoff wording.
- The prompt is persisted with the run and displayed in the run view (web and
  TUI transcript); it is not shown in the compact `ps` listing.
- A blank prompt preserves today's behavior exactly.

## Alternatives Considered

### Alternative 1: Phased rollout (CLI first, then web, then visibility)

- **Description**: Ship CLI pass-through as MVP, add the two web surfaces next,
  add run-view persistence/visibility last.
- **Pros**: Smallest first increment; validates kickoff framing before UI work.
- **Cons**: The three requested surfaces do not land together; the optional field
  is re-touched in every phase; disproportionate process overhead for one small
  field.
- **Why rejected**: The feature is fundamentally one optional field over a proven
  pattern; phasing adds coordination cost without reducing real risk.

### Alternative 2: Minimal pass-through, no persistence or visibility

- **Description**: All three surfaces accept the prompt, but it only feeds the
  first step's kickoff and is never stored or surfaced afterward.
- **Pros**: Leanest possible scope.
- **Cons**: Users cannot recall what a run was launched with — a real gap for
  reviewing interactive runs after the fact.
- **Why rejected**: Conflicts with the requirement to show the prompt in the run
  view; the persistence cost is small and the recall value is high.

## Consequences

### Positive

- All three entry points gain the capability simultaneously with a consistent UX.
- Reuses the `branch`-field plumbing pattern and the runner's existing inbound
  message support, keeping the change small and low-risk.
- Users can direct each run and later see what it was started with.

### Negative

- One additional optional field on the start contract and run record to maintain.

### Risks

- Mislabeling the user prompt as a prior-step handoff would confuse agents —
  mitigated by the distinct "user request for this run" framing.
- Long or sensitive prompts in the run view — mitigated by treating the prompt as
  ordinary run metadata and keeping it out of compact listings.

## Implementation Notes

Deferred to the TechSpec. The PRD intentionally avoids prescribing the field
name, RPC shape, or storage mechanism.
