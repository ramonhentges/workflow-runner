# ADR-001: V1 Scope for Daemon Mode

## Status

Accepted

## Date

2026-05-25

## Context

The workflow-runner today binds workflow lifecycle to the foreground process lifecycle: closing the terminal, an OS sleep, or any crash kills the agent subprocess and loses all progress. The target user (solo developer running 2-4 long agent workflows concurrently) needs (a) workflows that survive terminal close, (b) the ability to start and supervise multiple workflows from one CLI, (c) attach/detach of a TUI to any running workflow, (d) recovery from crashes by re-running the failed step with its original kickoff prompt, and (e) the ability to queue messages to an interactive step when no TUI is attached.

The codebase already has favorable seams: a hexagonal layering with a stateless-per-run Runner, a per-step MCP server that already binds to port `:0`, JSON-serializable `RunnerEvent`s, and an existing (though minimal) TUI detach path. There is no persistence layer, no `Run`/`Execution` model, no notion of a run id, and no IPC surface.

The council debate identified a real tension between keeping the parallel-runs scope (the headline feature) and the increased blast radius of one daemon crash affecting multiple workflows. The debate resolved by adding daemon-restart recovery (re-discover runs from disk and mark in-flight ones as `crashed`) to V1. A second tension on the meaning of "resume" resolved by renaming the verb to `retry-step` and surfacing a banner that the LLM output may differ from the original attempt.

## Decision

V1 of daemon mode will include the following capabilities, all behind a single binary with subcommands:

1. A background daemon process listening on a Unix domain socket at `$XDG_STATE_HOME/workflow-runner/daemon.sock` (default `~/.local/state/workflow-runner/daemon.sock`), with `0600` permissions and a lockfile to prevent double-spawn.
2. CLI subcommands: `daemon` (foreground run), `start <workflow.json>`, `attach <run-id>`, `detach`, `ps`, `send <run-id> <message>`, `retry-step <run-id>`, `stop <run-id>`, `doctor`.
3. Both manual (`workflow-runner daemon`) and auto-start (any other subcommand spawns the daemon if no socket is present).
4. A `Run` model with a stable id, current step id, status (`running | completed | failed | crashed`), and timing metadata. State persists to a per-run directory under `$XDG_STATE_HOME/workflow-runner/runs/<run-id>/` containing `meta.json` and `events.jsonl` (append-only log of all `RunnerEvent`s except `stream` events of kind `thought`).
5. Each run gets a fresh per-run MCP server on port `:0` and per-step agent subprocesses, as today.
6. The TUI becomes a UDS client. On attach it requests run state plus the last-step event backlog from disk, then live-streams subsequent events. Detach is clean and silent. User messages from a TUI or from `send` are durably queued on the daemon side so an interactive step survives detach.
7. Crash recovery preserves only the kickoff prompt for the failed step. `retry-step` re-runs the step from scratch with the original prompt. The CLI and TUI must surface a "↻ retrying step-N — LLM output may differ" banner so the semantic is unambiguous.
8. On daemon restart, the daemon discovers run directories, marks any `status: running` as `status: crashed`, and exposes them via `ps` for explicit `retry-step`. The daemon does **not** auto-resume crashed runs in V1.
9. Step outcome must be `fsync`'d to `meta.json` before the next step's `banner` event is emitted, guaranteeing that resume points to the correct step.
10. Per-run log retention: rotate `events.jsonl` when it exceeds 50 MB.

## Alternatives Considered

### Alternative 1: Minimal V1 — daemon + attach/detach + retry-step only, no parallel runs

- **Description**: Ship the daemon, single-workflow-at-a-time, attach/detach, and step retry first. Add concurrency in V2 after stability is proven.
- **Pros**: Smallest blast radius; fewer concurrency bugs in the first ship; easier to audit; faster to a working daemon.
- **Cons**: Cuts the headline user request (parallel runs from one terminal); leaves the daemon at near-zero value over today's tool until V2; defers the architectural choice that most affects the IPC and state design, risking a V2 rewrite.
- **Why rejected**: The user explicitly named parallel runs as the primary motivation; the architectural seams (per-run MCP server, per-run state dir, per-run event log) actually become *simpler* when designed for concurrency from day one than when retrofitted.

### Alternative 2: Maximal V1 — add full conversation persistence and auto-resume

- **Description**: Persist the full ACP session of each agent (not just kickoff prompts), and auto-resume crashed runs on daemon restart without user intervention.
- **Pros**: True "no work ever lost" story; matches LangGraph/Temporal-class durability; users never lose mid-thought context.
- **Cons**: Persisting and replaying ACP session state is a research project (LLM nondeterminism, agent-internal state, tool-call replay semantics); auto-resume silently spends tokens without consent.
- **Why rejected**: Out of scope for V1 by user decision ("Step + kickoff prompt only"). Auto-resume violates the principle of explicit, observable cost.

### Alternative 3: gRPC over UDS instead of line-delimited JSON

- **Description**: Use gRPC for the daemon protocol — strongly-typed schema, native streaming, ecosystem tooling.
- **Pros**: Compile-time safety; first-class bidirectional streaming for event subscriptions; protobuf evolution story.
- **Cons**: Heavy dependency footprint for a Bun/single-binary CLI; adds a code-generation step; opaque to ad-hoc debugging with `socat`/`nc`.
- **Why rejected**: A line-delimited JSON protocol over UDS is sufficient for a single-user, single-host daemon and is trivially debuggable; the gRPC machinery is overkill for the surface area V1 needs.

## Consequences

### Positive

- Workflows survive terminal close, SSH disconnect, and OS sleep (the headline reliability win).
- Multiple workflows can run in parallel from one CLI, supervised independently.
- Attach/detach matches the tmux/abduco mental model that CLI-native developers already have.
- The event log per run becomes a single load-bearing abstraction serving persistence, replay, audit, and resume — minimizing distinct mechanisms.
- The CLI message-queue capability is a market differentiator: no surveyed competitor offers headless message-send to a running interactive agent step.

### Negative

- A daemon crash now affects all in-flight runs instead of one. Mitigated by per-run isolation (separate MCP server, separate subprocess, separate log) and by the recovery-on-restart path.
- The CLI surface roughly doubles (8 new subcommands). Onboarding cost rises; mitigated by auto-start preserving the single-command zero-config UX for non-parallel users.
- Disk usage grows monotonically until rotation kicks in. Users running many short workflows will accumulate `runs/` entries that need manual cleanup until a V2 retention policy lands.

### Risks

- **Resume divergence:** Re-running a step with the same kickoff prompt is non-deterministic; users may expect continuation. Mitigation: rename `resume` to `retry-step` and emit a visible banner.
- **Daemon visibility under auto-start:** Users may not realize a daemon exists when things go wrong. Mitigation: `doctor` subcommand surfaces daemon health, socket state, orphaned subprocesses, and disk usage.
- **Outcome/banner ordering bug:** If a step outcome is not `fsync`'d before the next banner, a crash between them produces incorrect resume state. Mitigation: explicit ordering contract in the Runner; integration test that kills the daemon between step boundaries.
- **Auto-start race:** Two CLI invocations may try to spawn the daemon simultaneously. Mitigation: lockfile-based mutex with `flock` semantics; CLI retries on `EADDRINUSE`.
- **Cost blowup from parallelism:** Token spend scales with concurrent runs. Mitigation: `ps` surfaces per-run elapsed time and step count; `doctor` warns when active subprocess count crosses a threshold.

## Implementation Notes

- The Run id should be a short ULID or 8-char nanoid; long UUIDs are hostile to CLI use.
- The event log filter (exclude `stream` events of kind `thought`) must be applied at write time, not read time, so disk usage stays bounded.
- The lockfile should contain the daemon PID so `doctor` can detect stale locks from non-graceful exits.
- The TUI replay-on-attach should fetch from the last `banner` event onward by default, with a flag to request the full run history.
