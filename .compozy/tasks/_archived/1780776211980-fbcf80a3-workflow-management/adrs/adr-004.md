# ADR-004: Filename-addressed REST workflow CRUD with server-side domain validation

## Status

Accepted

## Date

2026-06-03

## Context

Workflows are `*.json` files under `<cwd>/workflows`. Today only `GET /workflows?cwd=`
(list) and the runner (loads by absolute path) touch them; there is no create,
read-one, update, or delete. We need a CRUD surface for the web app that fits
the existing Hono + `@hono/zod-openapi` route pattern, the `cwd`-scoped model,
and the path-based runner. We also need saved workflows to remain runnable, and
we must prevent path traversal when a client supplies a workflow name.

## Decision

Add REST endpoints under the existing `/workflows` resource, **addressing a
workflow by its bare name** (no extension) in the URL; the server appends `.json`
for every operation:

- `GET /workflows?cwd=` — list (existing; returns full `*.json` filenames)
- `GET /workflows/{name}?cwd=` — read one (returns the parsed workflow JSON)
- `POST /workflows?cwd=` — create (`{ name, workflow }`)
- `PUT /workflows/{name}?cwd=` — update; an optional new name in the body renames
  (the server moves the file)
- `DELETE /workflows/{name}?cwd=` — delete (run-aware, see ADR-003/ADR-006-run-guard)

`{name}` is validated as a safe basename (no `/`, `\`, `..`, or path separators);
the resolved file path must stay within `<cwd>/workflows`. On create/update the
posted `workflow` body is run through the existing domain validation
(`Workflow.fromJson`); a `WorkflowConfigError` maps to **HTTP 400
`WORKFLOW_INVALID`** via the existing `mapError`. The web editor mirrors the same
rules in zod for instant feedback, but the server is the source of truth.

## Alternatives Considered

### Alternative 1: Address by the workflow `id` field

- **Description**: Map the internal `id` to a file via an index; rename changes a display name only.
- **Pros**: Decouples identity from the filesystem.
- **Cons**: Requires an id→file index, risks id collisions within a project, and diverges from the path-based runner and existing list output.
- **Why rejected**: Adds machinery for no benefit; filename is already the stable handle everywhere else.

### Alternative 2: Lenient server (save any JSON)

- **Description**: Server only checks valid JSON + safe filename; validation is advisory in the editor.
- **Pros**: Allows saving incomplete drafts.
- **Cons**: Malformed workflows can land on disk and fail at run time, undermining the PRD goal that saved workflows are well-formed.
- **Why rejected**: Server-side enforcement is cheap (reuse `Workflow.fromJson`) and guarantees runnable files.

## Consequences

### Positive

- Clean REST surface consistent with existing routes; reuses domain validation and `mapError`.
- Bare-name URLs keep paths tidy; `.json` is an implementation detail of the store.
- Saved workflows are always structurally valid and runnable.

### Negative

- Authors cannot persist an intentionally-incomplete draft via the API.
- Two name representations coexist (list returns `who-is.json`; CRUD paths use `who-is`), so the web client strips the extension.

### Risks

- Path traversal via crafted names. *Mitigation:* strict basename validation and a containment check against the resolved `workflows` dir, rejected as 400.
- Concurrent edits overwriting each other (last-write-wins). *Mitigation:* acceptable for a local single-user tool; out of scope.

## Implementation Notes

- New file `src/app/api/routes/workflow-crud.ts` (or extend `workflows.ts`) registering the read-one/create/update/delete routes; schemas added to `src/app/api/schema.ts`.
- Delete and rename consult `RunManager` for active runs (see ADR-006).
- Write atomically (temp file + rename) to avoid partial files.
