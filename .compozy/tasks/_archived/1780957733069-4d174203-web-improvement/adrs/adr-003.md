# ADR-003: Drive the dashboard status filter from a typed URL search param (TanStack Router)

## Status

Accepted

## Date

2026-06-06

## Context

PRD feature F4 requires the five status summary cards to filter the runs list when clicked (Failed card → list shows only failed runs). The filter state must live somewhere that both the cards (to show the active selection) and the runs list (to filter rows) can read. The app already uses TanStack Router with typed routes and `validateSearch`, TanStack Query for the runs poll, and Zustand for the cwd store. The runs data itself is unchanged — filtering is purely a client-side view concern over the existing `useRuns` poll.

## Decision

Store the active status filter as a typed, optional search param on the dashboard (index) route via `validateSearch` — e.g. `?status=failed`. Cards navigate with `navigate({ search: { status } })` (toggling off when the active card is clicked again); the runs list reads `route.useSearch()` and filters the polled runs array by `status` before rendering. No new data fetch is introduced — the filter is applied to the already-polled array.

## Alternatives Considered

### Alternative 1: Component-local React `useState`

- **Description**: A single `useState<RunStatus | null>` in a dashboard container shared by cards and list.
- **Pros**: Simplest; no router or store changes.
- **Cons**: Filter resets on reload/navigation; not shareable or bookmarkable; reintroduces a container component purely to hold state.
- **Why rejected**: The router is already the natural home for view state; URL params cost the same effort and add persistence + shareability for free.

### Alternative 2: Zustand store

- **Description**: Add filter state to a global store like the existing cwd-store.
- **Pros**: Globally accessible.
- **Cons**: Heavier than needed for one view's transient filter; not URL-shareable; global state for a single-view concern is over-scoped.
- **Why rejected**: YAGNI — a global store for one screen's filter is unwarranted.

## Consequences

### Positive

- The filtered view is shareable, bookmarkable, and survives reload.
- No new data layer; filter is a pure transform over the existing 2s poll.
- Type-safe via `validateSearch`; an invalid `status` value coerces to "no filter".

### Negative

- The dashboard route gains a `validateSearch` parser that must be kept in sync with the `RunStatus` union.

### Risks

- **Invalid/stale param values** (e.g. a removed status). *Mitigation*: `validateSearch` whitelists the five known `RunStatus` values and falls back to `undefined` (no filter).

## Implementation Notes

`validateSearch` on `indexRoute` returns `{ status?: RunStatus }`, parsing only the five known values. The runs list filters `runs.filter(r => !status || r.status === status)`. The existing "All runs" toggle (`aria-pressed`) is orthogonal and preserved.
