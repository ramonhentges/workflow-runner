# ADR-002: Inbound-message kind discriminator for kickoff framing

## Status

Accepted

## Date

2026-06-12

## Context

The runner already delivers an inbound message to the entry step via
`runner.run(startStepId, startInboundMessage)`. `buildKickoffPrompt(step,
inboundMessage)` in `agent-session.ts` appends any non-null inbound message under
the fixed wording `"Context from previous step: {msg}"`.

This channel is shared by two distinct origins:

1. **Retry/resume** — `RunManager.retryStep` re-enters a step with the handoff
   message that was in flight; here "Context from previous step" is correct.
2. **Fresh start with an initial prompt** (this feature) — the entry step's
   inbound message is the *user's request for the run*, not a prior step's output.

The PRD requires the prompt be framed to the agent as the user's request, distinct
from handoff context (PRD Core Feature #2). We must distinguish the two origins at
the point where the kickoff text is built, without breaking the retry path.

## Decision

Carry a **kind discriminator** alongside the entry-step inbound message.
`runner.run` accepts the start inbound message together with its kind
(`"user-request" | "handoff"`). `buildKickoffPrompt` selects the framing label
from the kind:

- `user-request` → "User request for this run: {msg}"
- `handoff` → "Context from previous step: {msg}" (unchanged)

The fresh-start path (`startRun` → `#launchRunner` → `runner.run`) passes
`user-request`; the retry path passes `handoff`. Inter-step handoffs computed
inside the runner loop continue to frame as `handoff`. When there is no inbound
message (no prompt, non-retry start), behavior is byte-for-byte identical to today.

## Alternatives Considered

### Alternative 1: Separate `initialPrompt` parameter on `runner.run`

- **Description**: Add a dedicated `initialPrompt` argument distinct from the
  resume inbound message; the entry step frames it independently.
- **Pros**: Strong separation of the two concepts at the signature level.
- **Cons**: Two inbound channels into the entry step that must be reconciled
  (what if both are present?); more surface area than a single labeled channel.
- **Why rejected**: The two origins are mutually exclusive per run; one labeled
  channel expresses that more simply than two parameters.

### Alternative 2: Pre-frame the full kickoff text upstream in the daemon

- **Description**: Build the framed kickoff string in run-manager before it
  reaches the runner; leave `buildKickoffPrompt` untouched.
- **Pros**: No change to the runner/agent-session signatures.
- **Cons**: Splits kickoff-text construction across two layers; the domain runner
  loses ownership of how steps are framed; harder to keep mode-instruction wording
  consistent.
- **Why rejected**: Kickoff framing is domain logic and should stay in
  `buildKickoffPrompt`; smearing it into the daemon violates the layering.

## Consequences

### Positive

- The agent sees a clear "user request" label for initial prompts.
- The retry path is unchanged; one labeled channel covers both origins.
- No-inbound and retry behavior remain identical to today (no regression).

### Negative

- `runner.run` and `buildKickoffPrompt` signatures gain a kind parameter that all
  callers must supply.

### Risks

- A caller passing the wrong kind would mislabel the message — mitigated by the
  small, enumerable set of call sites (fresh start, retry) and unit tests asserting
  each label.

## Implementation Notes

- Add the kind type next to the existing inbound plumbing in `runner.ts`.
- `#launchRunner` gains the kind; `startRun` passes `user-request`, `retryStep`
  passes `handoff`.
