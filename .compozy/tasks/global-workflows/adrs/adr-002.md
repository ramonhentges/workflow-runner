# ADR-002: Store global workflows in the XDG state directory

## Status

Accepted

## Date

2026-06-10

## Context

ADR-001 fixed the product model: global workflows live in a single, fixed,
user-level home independent of any project. This ADR chooses that location on
disk.

The daemon already establishes a user-level storage root in
`src/infra/daemon/run-store.ts`: `resolveStorageRoot` returns
`(XDG_STATE_HOME ?? ~/.local/state)/workflow-runner`, which holds run state and
the daemon socket. Project workflows live under `<cwd>/workflows/*.json`. The
global store must be a single directory the daemon can resolve without any
`cwd`, using the same name/extension conventions as project workflows so the
existing `Workflow.load`, name validation, and atomic-write helpers apply
unchanged.

## Decision

Store global workflows as `*.json` files in
`(XDG_STATE_HOME ?? ~/.local/state)/workflow-runner/workflows/`, reusing the
daemon's existing storage root. Resolve the directory via the same
`resolveStorageRoot` convention used by the run store, append `workflows/`, and
create it lazily on first write (`mkdir -p`). File naming, the bare-name
addressing scheme, and JSON structure match project workflows exactly.

## Alternatives Considered

### Alternative 1: XDG config directory

- **Description**: Store under `(XDG_CONFIG_HOME ?? ~/.config)/workflow-runner/workflows/`.
- **Pros**: User-authored content arguably belongs in config, not state.
- **Cons**: Introduces a second user-level root the daemon must resolve and
  manage, distinct from the one it already owns.
- **Why rejected**: The daemon already centralizes user-level storage under the
  state root; adding a config root splits ownership for no functional gain.

### Alternative 2: Single dotfolder

- **Description**: Store under `~/.workflow-runner/workflows/`.
- **Pros**: Simple, no XDG split.
- **Cons**: Ignores the XDG convention the daemon already follows; not
  overridable via `XDG_STATE_HOME` (which tests and sandboxes rely on).
- **Why rejected**: Inconsistent with the established storage-root convention.

## Consequences

### Positive

- One user-level storage root for the daemon; global workflows sit beside run
  state under a single, `XDG_STATE_HOME`-overridable root.
- Tests and sandboxes can redirect the global store by setting
  `XDG_STATE_HOME`, exactly as they already do for run state.
- All existing project-workflow file helpers apply unchanged.

### Negative

- Conflates user-authored content with disposable run state under one root,
  blurring the state-vs-config distinction.

### Risks

- **Accidental loss if users clear state**: a user wiping `~/.local/state`
  loses global workflows. Mitigation: documentation; acceptable for an MVP with
  no sharing/backup requirement.

## Implementation Notes

Add a `resolveGlobalWorkflowsDir(env)` helper mirroring `resolveStorageRoot`,
returning `join(storageRoot, "workflows")`. The CRUD layer selects between this
directory and `<cwd>/workflows` based on the request scope (ADR-003).
