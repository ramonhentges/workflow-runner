# ADR-003: Step `agent` maps to an ACP session mode; `mode` is runner-side control

## Status

Accepted

## Date

2026-05-22

## Context

Each step in a workflow config carries two fields that look like they could both
drive the ACP session:

- `agent` — a persona id such as `architect-advisor`, `devils-advocate`, or
  `pragmatic-engineer`. The corresponding personas live under
  `.compozy/agents/<id>/AGENT.md`.
- `mode` — either `interactive` or `autonomous`.

ACP sessions have their own concept of a *session mode*: `session/new` returns
`availableModes`, and `setSessionMode` switches between them using an
agent-defined `modeId`. opencode exposes its selectable agents/personas as these
ACP session modes. The TechSpec must decide how the two config fields bind to the
session.

The risk is conflating them: treating `interactive`/`autonomous` as ACP session
modes would call `setSessionMode` with ids opencode does not recognize, while
ignoring `agent` would run every step as the same default persona.

## Decision

Bind the two fields to two different mechanisms:

- **`agent` → ACP session mode.** After creating a step's session, the runner
  calls `setSessionMode({ sessionId, modeId: step.agent })` to switch opencode
  into the persona named by the step. The step's `model` is applied with
  `unstable_setSessionModel({ sessionId, modelId: step.model })`.
- **`mode` → runner-side control only.** `interactive` and `autonomous` never
  reach ACP. They are interpreted entirely by the runner: `interactive` shows the
  input field and lets the user drive turns; `autonomous` hides the input field,
  sends a single kickoff prompt, and lets the agent run to its handoff/finish.

## Alternatives Considered

### Alternative 1: Treat `mode` as the ACP session mode

- **Description**: Call `setSessionMode` with `interactive`/`autonomous` and
  derive the persona some other way.
- **Pros**: One obvious-looking mapping from a field named "mode".
- **Cons**: opencode has no `interactive`/`autonomous` mode ids, so the call
  fails; leaves no channel for selecting the persona.
- **Why rejected**: Factually incorrect — those are not valid opencode mode ids.

### Alternative 2: Ignore ACP session modes; inject the persona via the prompt

- **Description**: Leave the session in its default mode and prepend the
  persona's `AGENT.md` text into the kickoff prompt.
- **Pros**: No dependency on `setSessionMode` or `availableModes`.
- **Cons**: Bypasses opencode's own persona system; the persona is not a true
  session mode and may not influence tool defaults or model routing the same way.
- **Why rejected**: opencode already models personas as session modes;
  `setSessionMode` is the supported, first-class path.

## Consequences

### Positive

- Each field maps to exactly one mechanism; no conflation.
- The persona is applied through opencode's native session-mode system.
- `interactive`/`autonomous` stay a pure UI/turn-driving concern, which keeps the
  TUI logic simple and protocol-independent.

### Negative

- The runner depends on `step.agent` being a valid `modeId` in the session's
  `availableModes`; an unknown persona is a step failure.
- Model selection uses `unstable_setSessionModel`, an unstable ACP method that
  may change.

### Risks

- `step.agent` not present in `availableModes`. Mitigation: validate `step.agent`
  against `availableModes` right after session creation and halt-and-report
  (consistent with the PRD failure model) if it is missing.
- `unstable_setSessionModel` is removed or changed upstream. Mitigation: isolate
  the call in the session-setup function so a future replacement is a one-line
  change; treat a model-set failure as a step failure.

## Implementation Notes

Session setup order per step: `newSession` → validate `step.agent` against
`availableModes` → `setSessionMode(step.agent)` → `setSessionModel(step.model)` →
kickoff. The kickoff prompt is composed of the step `description` and the inbound
handoff message (see TechSpec).
