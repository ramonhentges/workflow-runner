# ADR-006: Read-only historical events endpoint in V1

## Status

Accepted

## Date

2026-05-29

## Context

The WebSocket attach endpoint (ADR-004) streams a run's events: it replays a backlog on
connect and tails live events, with `?fromSeq=N` resume. That covers the *live view*, but a UI
also needs a non-streaming way to **pull a slice of already-recorded events** — e.g. to render
one step's transcript on a detail page, to page through history without holding a socket open,
or to fetch events accumulated since a known sequence after the UI was closed.

The PRD deferred "historical event-range retrieval (`GET /runs/:id/events?fromSeq=N&toSeq=M`)"
to V2 as part of the "replay & time-travel" direction. In review the user asked to bring a
narrower form of it into V1. The capability is cheap: `EventLog.readEventsSince(fromSeq)`
already exists (with a hard cap and a `truncated` flag), every `EventLogEntry` already carries
`stepId`, and terminal runs are already readable via `RunManager.openEventLog` (the attach
handler does exactly this).

The distinction that keeps the V2 non-goal coherent: this is a **read** of events that already
exist. It does not fork a run, restart from a past step with modified input, or add a second
streaming transport (SSE). Those — the parts that make "replay & time-travel" a distinct,
larger feature — remain V2.

## Decision

**Add a read-only `GET /runs/:id/events` endpoint to V1**, filterable by `fromSeq` and
`stepId`:

- `?fromSeq=N` → entries with `seq > N`.
- `?stepId=X` → entries whose `stepId === X`.
- both → that step's entries with `seq > N` (paging within a step).
- neither → full history, capped, with `truncated: true` when the cap is hit.
- Response: `{ entries: RunEvent[], truncated: boolean }` (same `RunEvent` schema as attach).
- Works for running and terminal runs; `:id` accepts id or unambiguous slug-prefix like the
  other endpoints. Unknown run → 404, ambiguous prefix → 409.

Implementation reuses `RunManager.openEventLog` + `EventLog.readEventsSince` and filters by
`stepId` in the handler — the same primitives the WS attach handler uses. No `toSeq` (not
requested; YAGNI). No new `RunManager` method beyond what attach already relies on.

## Alternatives Considered

### Alternative 1: Keep history retrieval entirely in V2 (PRD's original deferral)

- **Description**: Ship only the WS attach stream in V1; any historical pull waits for the V2
  replay feature.
- **Pros**: Smallest V1 surface; the V2 boundary stays exactly as the PRD drew it.
- **Cons**: A dashboard cannot render a step's transcript or page history without opening (and
  parsing the backlog of) a WebSocket per view — awkward for a read-only panel. The data and
  the read primitive already exist, so deferral buys little.
- **Why rejected**: The user needs it for the UI, and the marginal cost over the existing
  `readEventsSince` is near zero; only the genuinely larger parts of replay (fork, SSE) stay
  deferred.

### Alternative 2: stepId-only (no sequence filter)

- **Description**: `?stepId=X` only; sequence paging stays on the WS endpoint.
- **Pros**: Simplest query.
- **Cons**: No way to fetch "everything since seq N" without a socket; the cheap `fromSeq`
  filter is already native to `readEventsSince`.
- **Why rejected**: `fromSeq` is free given the underlying read; supporting both is strictly
  more useful at no real cost.

## Consequences

### Positive

- A UI can render per-step transcripts and page history with plain HTTP GETs, no socket.
- Reuses proven primitives (`openEventLog`, `readEventsSince`, the cap + `truncated` flag).
- Sharpens the V2 boundary: "replay & time-travel" now means specifically fork-from-seq and
  SSE, not historical reads.

### Negative

- One more endpoint and query schema in V1.
- A no-filter call on a long run does a capped full read; large pulls cost disk I/O (bounded by
  `EVENT_LOG_BACKLOG_LIMIT`).

### Risks

| Risk | Mitigation |
|---|---|
| Unbounded memory/IO on a no-filter pull of a huge run | Inherit `EventLog`'s existing hard cap (`EVENT_LOG_BACKLOG_LIMIT`) + `truncated` flag; document that callers page with `fromSeq`. |
| `stepId` filter on a step whose events predate the in-memory ring forces a disk read | Acceptable: `readEventsSince` already falls through to disk; same path attach uses. |
| Scope creep back toward V2 replay | This ADR fixes the line: read-only pull only; no fork, no modified-input restart, no SSE. |

## Implementation Notes

- New thin handler in `src/app/api/` alongside the other HTTP routes; obtains the event log via
  `RunManager.openEventLog(runId)` (owns/closes the handle for terminal runs exactly as
  `run-attach.ts` does), calls `readEventsSince(fromSeq ?? 0)`, then filters by `stepId` when
  present.
- Add `EventsQuery` (`{ fromSeq?: number; stepId?: string }`) and `EventsPage`
  (`{ entries: RunEvent[]; truncated: boolean }`) to `src/app/api/schema.ts`.
- This endpoint is HTTP-only; it is **not** added to the JSON-RPC surface (no consumer there).
