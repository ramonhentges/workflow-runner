# ADR-002: V1 dashboard and form-migration scope refinements (5 status cards, visual-primitives-only forms, no IDE column, browser-local theme)

## Status

Accepted

## Date

2026-06-06

## Context

ADR-001 locked the strategic direction: adopt shadcn/ui across the entire web app in V1, executed as a fixed sequence of small per-feature PRs (StatusBadge first), with the ⌘K command palette and live SSE updates deferred to V2. It left four scope-shaping questions open (recorded in `_idea.md` "Open Questions"):

1. How the dashboard summary cards should represent the five run statuses (`running` / `completed` / `failed` / `crashed` / `aborted`) given limited card real estate.
2. Whether the form-heavy features (workflow editor + step/edges/agent-model fields, start-run form) migrate to shadcn `Form`/`Controller` wholesale, or only swap visual primitives while leaving the react-hook-form + zod wiring intact.
3. Whether the redesigned runs list needs an explicit IDE column/badge in V1.
4. How the light/dark theme choice is persisted in V1.

These four choices materially affect V1 scope, test-churn risk, and the boundary with the V2 "mission-control" north star, so they are recorded together here before the PRD is drafted.

## Decision

1. **Five separate status cards** — one card each for Running, Completed, Failed, Crashed, Aborted, derived client-side from the existing `listRuns` 2s poll. Each card is click-to-filter against the runs list. The Failed card is visually emphasized when its count is non-zero. Fully explicit at the top level; no grouping or hover-only breakdown.
2. **Visual-primitives-only form migration** — swap native inputs/labels/selects/buttons for shadcn `Input`/`Label`/`Select`/`Button` primitives while preserving the existing react-hook-form + zod wiring (`useForm`, `register`, `control`, `zodResolver`) untouched. No adoption of shadcn `Form`/`FormField`/`Controller` wrappers in V1.
3. **No IDE column in V1** — the runs list stays focused on the GitHub-Actions-style columns (status → workflow → current step → started → duration). Per-step IDE visualization is held for the V2 mission-control step-journey view, where it conveys a multi-IDE journey rather than implying one IDE per run.
4. **Browser-local theme persistence** — the theme provider defaults to system preference; a user override is saved in the browser (`localStorage`). No daemon-side preference endpoint in V1.

## Alternatives Considered

### Alternative 1 (cards): grouped / outcome-based cards

- **Description**: 3–4 cards that fold `crashed` + `aborted` (and optionally `failed`) into an "Other" or "Needs attention" card with a hover/click breakdown.
- **Pros**: Fewer cards, calmer row, arguably reinforces the 5-second glance.
- **Why rejected**: The decision owner chose full explicitness; each terminal status is meaningful triage signal and hiding crashed/aborted behind a rollup adds a click to see what actually happened.

### Alternative 2 (forms): full shadcn `Form` with `Controller` wrappers

- **Description**: Adopt `<Form>`/`<FormField>`/`<FormItem>`/`<FormMessage>` with `<Controller>` across every field.
- **Pros**: Most idiomatic and internally consistent shadcn form pattern.
- **Why rejected**: Highest test-churn risk against the 19-file suite (`getByLabelText`, form `data-testid`s); contradicts ADR-001's "thin structural swaps, don't refactor internals in the same PR" discipline. Can be revisited post-V1 if desired.

### Alternative 3 (IDE column): show an IDE badge per row in V1

- **Description**: Render the step's IDE (`opencode`/`claude-code`/`codex`/`gemini`) as a badge in each runs-list row.
- **Pros**: More information density now.
- **Why rejected**: A single flat row cannot express a multi-IDE handoff journey and risks implying one IDE per run; the value lands properly in the V2 step-journey view.

### Alternative 4 (theme): daemon-side preference

- **Description**: Persist the theme server-side so it follows the user across browsers/devices.
- **Pros**: Cross-device consistency.
- **Why rejected**: New endpoint + plumbing for a single-user, local-first tool — disproportionate. `localStorage` is the standard, zero-backend approach.

## Consequences

### Positive

- All four V1 boundaries are explicit before drafting, removing guesswork from the PRD and TechSpec.
- Visual-primitives-only forms keep the form tests stable and the per-feature PRs thin, directly honoring ADR-001's sequencing discipline.
- Deferring the IDE column keeps a clean, uncluttered V1 list and reserves IDE journey richness as a distinct V2 value proposition.
- Browser-local theme adds zero backend surface.

### Negative

- Five cards consume more horizontal space and are busier than a grouped layout; on narrow viewports they must wrap or scroll.
- Visual-primitives-only forms leave a stylistic inconsistency (not "full" shadcn form idiom) that a future pass may want to close.

### Risks

- **Card responsiveness** — five cards may crowd small windows. *Mitigation*: responsive grid that wraps; the count + label remain legible at all widths.
- **`Select` swap in forms** — replacing native `<select>` with shadcn `Select` is the one place the "visual-only" swap still changes the DOM/interaction model. *Mitigation*: treat each `Select` swap as its own selector-audit checkpoint and carry `data-testid`s/roles forward.

## Implementation Notes

These refinements sit inside ADR-001's fixed PR sequence; they do not change the order (tokens → shell → table → cards → remaining features → polish). The five-card decision lands in the cards PR; the visual-primitives-only decision governs every form-feature PR; the IDE-column deferral is simply an absence; the theme decision lands in the polish PR alongside the `ModeToggle`.
