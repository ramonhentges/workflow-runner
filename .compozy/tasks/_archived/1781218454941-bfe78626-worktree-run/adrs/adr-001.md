# ADR-001: Opt-in per-run git worktree isolation with a user-provided branch

## Status

Accepted

## Date

2026-06-11

## Context

Runs currently execute in a single working directory: the CLI passes `process.cwd()` and the web UI lets the user pick a `cwd`. The agent subprocess is spawned directly in that directory. The daemon already allows up to 16 concurrent runs, but when several runs target the same repository they share one working tree. Two agents can read the same file, edit it independently, and write back — the second write silently erases the first agent's changes, with no warning to either side.

Git worktrees are the industry-standard primitive for solving exactly this: each run gets its own checked-out working directory and branch while sharing one `.git` object store, so file-level edits never collide and creation stays cheap.

We needed to decide how much of the worktree lifecycle the tool owns and how isolation is triggered.

## Decision

Add **opt-in, per-run** git worktree isolation. When a user starts an isolated run, they supply a **branch name**. If that branch exists, the worktree checks it out; if not, the tool creates the branch off the current repository state. The run executes inside that worktree instead of the user's working directory. The worktree path and branch are surfaced wherever the run is displayed (CLI `ps`/attach, web run details).

When the run ends — success or failure — the worktree and its branch are **left intact**. The tool never deletes the agent's work; the user inspects, diffs, commits, or merges it with their own git tooling. If the branch already has a worktree, the run **reuses** it so the user can extend in-progress work (refined in [ADR-005](adr-005.md)). Requesting isolation when the cwd is not inside a git repository fails clearly at start.

The tool does **not** auto-clean worktrees, manage worktree removal, or perform any merge/PR step in this effort.

## Alternatives Considered

### Alternative 1: Always-on isolation for any git repo

- **Description**: Every run inside a git repo automatically gets a fresh worktree.
- **Pros**: Maximum safety; no decision required from the user.
- **Cons**: Changes default behavior for existing users; forces worktree semantics on simple single-run cases.
- **Why rejected**: User wants isolation to be explicit and backward-compatible; opt-in keeps today's behavior as the default.

### Alternative 2: Isolation + managed lifecycle (Approach B)

- **Description**: Approach A plus tool-owned worktree removal/listing and committed-state status.
- **Pros**: Convenience; no need to drop to raw git for cleanup.
- **Cons**: Adds UX surface and edge cases (dirty worktrees, detached state) beyond the core problem.
- **Why rejected**: User prefers to manage cleanup via their own git tooling for now; YAGNI.

### Alternative 3: Isolation + merge/review flow (Approach C)

- **Description**: Approach A plus auto-merge of the run branch back to base or PR creation.
- **Pros**: End-to-end "run produces a reviewable unit" story.
- **Cons**: Large scope — merge-conflict handling, base-branch policy, remote/PR integration.
- **Why rejected**: The stated goal is isolation, not merging; merging is explicitly out of scope.

### Alternative 4: Always auto-generated, never-reused branch

- **Description**: Each isolated run always gets a unique new branch; existing branches are never checked out.
- **Pros**: No branch-collision handling.
- **Cons**: Cannot resume or continue work on an existing branch.
- **Why rejected**: User explicitly wants an existing branch checked out when it already exists.

## Consequences

### Positive

- Concurrent runs against the same repo no longer clobber each other's file edits.
- The user's active working tree and branch are never touched by an isolated run.
- Reusing an existing branch lets a run continue prior work; the run aggregate already persists `cwd`, so the isolated path round-trips through restarts.

### Negative

- The user is responsible for cleaning up worktrees and branches afterward; orphaned worktrees can accumulate.
- Concurrent isolated runs must use distinct branches to stay isolated; two runs naming the same branch share one worktree (reuse, [ADR-005](adr-005.md)) and can clobber each other — that constraint is pushed onto the user.

### Risks

- A requested branch may already have a worktree (including another active run); rather than failing, the run reuses that worktree ([ADR-005](adr-005.md)). The remaining hard-failure case is a non-worktree directory occupying the computed path. Mitigation: detect an existing worktree and reuse it; surface a precise error only for a genuine path conflict.
- Uncommitted agent work in a preserved worktree could be lost if the user later prunes worktrees carelessly. Mitigation: clearly surface the path and that work is preserved, not managed.

## Implementation Notes

Deferred to TechSpec. The `Run` aggregate and `RunSnapshot` already carry `cwd`; the isolated worktree path is the natural value to store there.
