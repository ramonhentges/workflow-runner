# ADR-001: Form-based workflow authoring now, visual canvas deferred

## Status

Accepted

## Date

2026-06-03

## Context

Users need to author and edit workflows (ordered steps plus the handoff edges
between them) from the web app. Two authoring models were viable: a structured
form (ordered step list with per-step fields and an edges sub-section) or a
visual graph canvas (drag-and-drop nodes with drawn edges). Today's real
workflows are linear handoff chains (`who-is` = 2 steps, `multi-agent` = 4
steps, all linear), and the underlying data model is a simple `steps[]` +
`edges[]` shape that already has domain validation.

## Decision

Ship a **form-based step editor** as the authoring surface for this feature: an
ordered list of steps, each with fields (id, ide, agent, model, mode,
description) and an edges sub-section, with add/remove/reorder and real-time
validation. The **visual graph canvas is explicitly deferred to a later phase**
as a topology view that will reuse the same per-step (node) configuration form.

## Alternatives Considered

### Alternative 1: Visual graph canvas from the start

- **Description**: Drag-and-drop nodes and drawn edges as the primary authoring surface, with per-node config forms.
- **Pros**: Matches the 2026 norm; best for visualizing branching and cross-IDE handoffs; impressive UX.
- **Cons**: New canvas dependency and layout/state complexity; heavier to test; still requires the per-node config form regardless, so it adds surface rather than replacing it; little payoff while workflows stay linear.
- **Why rejected**: Mostly decoration over a form we must build anyway, given current linear workflows. Cost outweighs near-term value.

### Alternative 2: Raw JSON editor

- **Description**: A code editor over the workflow JSON with schema validation and error highlighting.
- **Pros**: Minimal UI; power-user friendly; reuses validation directly.
- **Cons**: No guardrails for structured editing; easy to produce invalid or confusing files; poor discoverability for agent/model/ide choices.
- **Why rejected**: Does not deliver the guided, validated authoring experience the feature is meant to provide.

## Consequences

### Positive

- Fastest path to working, fully validated authoring on the existing web stack.
- Maps 1:1 to the `steps[]` + `edges[]` data model and reuses domain validation.
- Keeps the door open: the deferred canvas reuses the node-config form.

### Negative

- Handoff topology is read as fields rather than as a picture; branching is less glanceable until the canvas phase lands.

### Risks

- If workflows become genuinely branch-heavy sooner than expected, the form may feel limiting. Mitigation: the canvas phase is pre-planned and reuses the form.

## Implementation Notes

The canvas, when added, is a visualization/topology layer over the same data and
the same node configuration form; it is not a rewrite of authoring.
