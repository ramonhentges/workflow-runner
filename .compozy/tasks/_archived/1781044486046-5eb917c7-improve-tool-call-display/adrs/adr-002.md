# ADR-002: Append-each-update, fold-by-id tool-call lifecycle

## Status

Accepted

## Date

2026-06-08

## Context

ADR-001 established that tool calls become a first-class, persisted,
id-keyed run event. ACP emits several updates over a single call's life
(`tool_call` then one or more `tool_call_update`s: pending → in_progress →
completed/failed). The run's durable store (`src/infra/daemon/event-log.ts`)
is an append-only JSONL log with monotonic sequence numbers, a bounded
in-memory ring, and size-based rotation. We must decide how a call's multiple
updates land in that log and how consumers render exactly one entry per call.

## Decision

Each ACP update for a call is emitted and persisted as its own `tool_call`
`RunnerEvent`, carrying the stable `toolCallId` and the call's latest resolved
display state. The append-only log is left exactly as-is — multiple persisted
events may share a `toolCallId`.

Consumers fold by `toolCallId`: the TUI keeps a `Map<toolCallId, element>` and
mutates the existing element in place; the web reducer locates the transcript
item with the matching `toolCallId` and replaces it in position. Folding is
pure last-event-wins, so live rendering, re-attach backlog, and reopen of a
finished run all converge to the same final state.

To keep consumers dumb, the agent session maintains a small per-session
accumulator that merges each partial ACP update into the call's full known
state before emitting, so every `tool_call` event carries a complete display
view rather than a delta.

## Alternatives Considered

### Alternative 1: Coalesce to one persisted entry per call

- **Description**: Rewrite/replace the call's single log record as its status
  changes so only one record ever exists.
- **Pros**: Fewer log entries; no folding needed on read.
- **Cons**: Requires mutating immutable append-only JSONL — in-place rewrite or
  a compaction pass — breaking the log's monotonic-seq, ring, and rotation
  guarantees.
- **Why rejected**: Disproportionate change to a load-bearing, well-tested
  component for a cosmetic saving; folding on read is trivial and localized.

### Alternative 2: Emit deltas; consumers merge fields

- **Description**: Ship only the fields that changed in each update and let each
  consumer merge them into prior state.
- **Pros**: Smallest event payloads.
- **Cons**: Pushes identical merge logic into both the TUI and the web client,
  inviting drift — the exact risk ADR-001 set out to avoid.
- **Why rejected**: Centralizing the merge in one server-side accumulator and
  shipping a complete view keeps both surfaces purely last-wins.

## Consequences

### Positive

- No changes to the event log's storage mechanics or guarantees.
- Replay is trivially correct: the last event per id is the final state.
- Both consumers stay simple (last-wins fold, no field merging).

### Negative

- A call produces 2–4 persisted events instead of one, modestly increasing log
  volume (well within the existing ring/rotation budget).

### Risks

- A stray duplicate or out-of-order update could momentarily show a stale
  state; mitigated by monotonic seq ordering already enforced on read and by
  last-wins fold.

## Implementation Notes

- The per-session accumulator lives in the ACP `AgentSession` and is discarded
  when the session/step ends; tool-call ids are unique per session.
- The TUI clears its `toolCallId → element` map on each `banner` event to bound
  memory across steps.
