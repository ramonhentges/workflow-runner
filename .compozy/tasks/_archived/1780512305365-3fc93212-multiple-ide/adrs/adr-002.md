# ADR-002: IdeProfile registry with a dispatching session factory

## Status

Accepted

## Date

2026-06-02

## Context

The runner drives every step through `RunnerAgentSessionFactory.create(args)`, which
already receives the full `step`. Today the only implementation,
`AcpAgentSessionFactory`, builds an `AgentSession` whose `start()` hardcodes opencode:
the spawn command `opencode acp` with `OPENCODE_ENABLE_QUESTION_TOOL=1`, validation of
`step.agent` against opencode's `configOptions` "mode" select, `setSessionMode(step.agent)`,
and `unstable_setSessionModel(step.model)`. Everything else in `start()` — ACP
`initialize`, `newSession` with the workflow MCP server, kickoff prompt, the
interactive/autonomous outcome race, and `dispose()` — is already agent-agnostic.

PRD ADR-001 commits to per-step IDE selection across four agents (opencode, Claude
Code, Codex CLI, Gemini CLI) at full parity. The four agents expose persona/agent and
model selection differently over ACP, and each has a distinct ACP entrypoint. We need
a structure that isolates these per-agent differences without duplicating the shared
ACP lifecycle.

## Decision

Introduce an `IdeProfile` abstraction and a dispatching factory; keep a single
generalized `AgentSession`.

- `IdeProfile` captures everything that differs per agent:
  - `spawn`: command, args, and env additions (statically declared per profile).
  - `configureSession(connection, sessionId, step)`: fully owns how that agent maps
    `step.agent` and `step.model` onto its ACP surface (`setSessionMode`,
    `unstable_setSessionModel`, `configOptions` validation, or nothing).
- A static profile registry maps the `ide` string to its `IdeProfile`. The four
  supported agents are registered with hardcoded spawn commands and env.
- `AgentSession.start` becomes profile-driven: it spawns from `profile.spawn`, runs the
  shared ACP lifecycle, and delegates mode/model selection to
  `profile.configureSession`.
- A dispatching `RunnerAgentSessionFactory` (the generalized successor to
  `AcpAgentSessionFactory`) looks up `step.ide` in the registry. An unrecognized `ide`
  throws, which the runner already converts into a fail-at-the-step outcome naming the
  step and value.
- New files live under `src/infra/acp/`; no new package or directory.

## Alternatives Considered

### Alternative 1: One RunnerAgentSessionFactory per IDE

- **Description**: A separate factory implementation per agent, chosen by a dispatcher.
- **Pros**: Strong per-agent isolation.
- **Cons**: Duplicates the shared ACP lifecycle (init, newSession, kickoff, outcome
  race, dispose) four times; drift risk across copies.
- **Why rejected**: The lifecycle is already agent-agnostic; duplication buys nothing.

### Alternative 2: Subclass AgentSession per IDE

- **Description**: An `AgentSession` base class with one subclass per agent overriding
  the IDE-specific steps.
- **Pros**: Reuses the shared lifecycle.
- **Cons**: Inheritance couples the lifecycle to a class hierarchy; the only real
  variation (spawn + configureSession) is better expressed as data/composition.
- **Why rejected**: Composition via `IdeProfile` is simpler and keeps `AgentSession`
  closed for modification when adding agents.

## Consequences

### Positive

- Adding an agent is one registry entry plus its `configureSession`; the shared
  lifecycle and the runner/MCP contract are untouched.
- Per-agent ACP quirks are quarantined in one place per agent.
- Unknown-`ide` handling reuses the existing fail-at-the-step path for free.

### Negative

- `configureSession` is a per-agent surface that must be maintained as each agent's
  ACP bridge evolves.

### Risks

- A non-opencode agent's ACP bridge may not support persona or model selection the way
  the step fields assume. Mitigation: each profile's `configureSession` decides how to
  map (or reject) the fields; an unsupported field surfaces as a clear step error
  rather than silent divergence. Exact mappings for Claude Code, Codex, and Gemini are
  confirmed during implementation and the manual E2E pass.
- Hardcoded spawn commands assume the agent binaries are on PATH with known
  entrypoints. Mitigation: documented prerequisites; env-var/config overrides are a
  deliberate future increment, not MVP.

## Implementation Notes

`AcpAgentSessionFactory` is renamed/generalized into the dispatching factory and
continues to be constructed in `daemon.ts:resolveSessionFactory()`. The `FixtureSessionFactory`
used in tests is unaffected (it implements the same port). `availableModeIds` moves
into the opencode profile's `configureSession`.
