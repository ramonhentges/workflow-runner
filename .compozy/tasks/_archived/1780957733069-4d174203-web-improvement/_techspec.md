# TechSpec: Web UI Improvement — Full shadcn Adoption + Dashboard Command Center

## Executive Summary

This effort migrates the `web/` SPA to use shadcn/ui across the entire app and adds a dashboard command center, executed as a fixed sequence of small, independently-shippable PRs (per `_prd.md` and ADR-001). The work is almost entirely **front-end structural/visual replacement**: no daemon endpoints change, no new data is fetched, and the existing TanStack Router / TanStack Query (2s poll) / Zustand / react-hook-form + zod wiring is preserved. New shadcn primitives are added via the shadcn CLI (ADR-001 components.json: new-york / zinc / CSS variables); a single semantic status-token system + reusable `StatusBadge` is built first to quarantine the volatile color coupling; the dashboard gains five status cards that filter the runs list via a typed URL search param (ADR-003); a hand-rolled theme provider drives system/light/dark with `localStorage` persistence (ADR-004).

The **primary technical trade-off** is the Radix-backed shadcn `Select` adoption (ADR-005): it delivers full visual consistency at the cost of changing the dropdown DOM/interaction model (Radix, not native `<select>`), which forces those two form fields from `register` onto react-hook-form `Controller` and requires rewriting the `selectOptions`-based tests plus jsdom pointer-API shims. Every other form change is a thin visual-primitive swap that preserves wiring and tests. The 19-file Vitest + MSW suite is the regression gate for each PR; the discipline is "carry every `data-testid`/role/label forward, audit selectors per PR, land green before the next."

## System Architecture

### Component Overview

The app is a Vite SPA mounted in `main.tsx` (`QueryClientProvider` → `RouterProvider`). Routes (`router.tsx`) render feature components inside `AppShell`. This spec touches the shell, the dashboard, the run view, and the workflow/start-run forms, plus two new cross-cutting primitives.

New / changed components and their responsibilities:

- **`components/ui/*` (shadcn primitives)** — `card`, `table`, `badge`, `skeleton`, `select`, `sidebar`, `alert`, `dialog`, `dropdown-menu`, `separator`, `tooltip` (added on demand, only what each PR consumes). Generated by the shadcn CLI. Pure presentational primitives consumed by features.
- **`StatusBadge` (new, cross-cutting)** — single source of truth mapping a `RunStatus` to its semantic color token + lucide icon + label. Consumed by the runs list (F3) and status cards (F4). Built first (F1) so every status rendering is centralized.
- **Status design tokens (`index.css`)** — five semantic status color variables added to `:root` and `.dark` (+ `@theme inline` mappings so Tailwind utilities resolve them). Consumed only through `StatusBadge`.
- **`ThemeProvider` + `useTheme` + `ModeToggle` (new, F6)** — context that resolves system preference, toggles `.dark` on `documentElement`, and persists to `localStorage`. Mounts in `main.tsx`; `ModeToggle` lives in the shell header.
- **App shell (F2)** — `AppShell` re-expressed with shadcn `sidebar-07` primitives (`SidebarProvider`/`Sidebar`/`SidebarInset`), preserving the three nav `Link`s, `DaemonStatus`, and `CwdSwitcher`.
- **Dashboard (F3 + F4)** — `RunsTable` migrated to shadcn `Table` with icon-first rows; new `StatusSummaryCards` derived client-side from `useRuns`; both read the `status` URL search param.
- **Forms & run view (F5)** — `WorkflowEditor`/`StepFields`/`EdgesField`, `StartRunForm`, and run-view (`RunView`/`RunControls`/`Transcript`/`InputBox`/`StepProgress`) re-skinned with shadcn primitives; native `<select>` → shadcn `Select` (ADR-005).

Data flow is unchanged: `useRuns` (TanStack Query, `refetchInterval: 2000`) → runs array → cards compute counts client-side and the list filters by the URL `status` param. No component fetches new data.

## Implementation Design

### Core Interfaces

`StatusBadge` is the primary new type other components depend on. It centralizes the status→{token,icon,label} mapping that today is scattered in `statusClass()`:

```tsx
// web/src/components/status-badge.tsx
import type { RunStatus } from '@/lib/api/types'

export interface StatusBadgeProps {
  status: RunStatus
  /** icon-only (table cell) vs icon+label (cards, banners) */
  showLabel?: boolean
  className?: string
}

// internal mapping — the single source of truth for status presentation
interface StatusMeta {
  label: string
  icon: LucideIcon
  /** token class pair, e.g. 'text-status-failed bg-status-failed/10' */
  tone: string
}
declare const STATUS_META: Record<RunStatus, StatusMeta>

export function StatusBadge(props: StatusBadgeProps): JSX.Element
```

The dashboard filter param (ADR-003), parsed on the index route:

```tsx
// web/src/router.tsx — indexRoute
const RUN_STATUSES = ['running','completed','failed','crashed','aborted'] as const
function parseStatus(v: unknown): RunStatus | undefined {
  return (RUN_STATUSES as readonly string[]).includes(v as string)
    ? (v as RunStatus) : undefined
}
// validateSearch: (s) => ({ status: parseStatus(s.status) })
```

The theme context (ADR-004):

```tsx
// web/src/components/theme-provider.tsx
export type Theme = 'system' | 'light' | 'dark'
export interface ThemeContextValue {
  theme: Theme
  setTheme: (t: Theme) => void
}
export function useTheme(): ThemeContextValue
```

### Data Models

No new domain or wire models. All types already exist in `web/src/lib/api/types.ts` and are reused as-is:

- `RunStatus = 'running' | 'completed' | 'failed' | 'crashed' | 'aborted'` — drives `StatusBadge`, the five cards, and the filter param.
- `RunSummary` — the row/card source (`status`, `slug`, `workflowPath`, `currentStepId`, `startedAt`, `endedAt`, `attachedCount`). Duration is derived in-view from `startedAt`/`endedAt` (no new field).

Card counts are a pure client-side reduction over the polled `RunSummary[]`:

```ts
const counts = runs.reduce((acc, r) => { acc[r.status]++; return acc }, zeroCounts())
```

### API Endpoints

None. This spec adds and changes no daemon endpoints. The dashboard continues to rely on the existing `listRuns` poll (`useRuns`, 2s). Live SSE updates are explicitly out of scope (PRD Non-Goals; ADR-001).

## Integration Points

No external services. The only "integration" is the build-time shadcn CLI (`bunx shadcn@latest add <component>`) which writes primitives into `src/components/ui` and installs Radix peer deps; this requires network access during the relevant PRs (ADR-001 sourcing decision). No auth/retry concerns.

## Testing Approach

### Unit Tests

- **Strategy:** Preserve the existing Vitest + MSW + Testing Library setup. The suite is the regression gate per PR (PRD KPI: 0 regressions). Every migrated component keeps its `data-testid`s, ARIA roles, and labels so existing assertions keep passing; new behavior gets new tests.
- **New tests:** `StatusBadge` (all 5 statuses render correct label/icon/tone, icon-only vs labeled); `StatusSummaryCards` (counts from a mocked runs array, Failed emphasis when non-zero, click navigates with the right `status` search param); `ThemeProvider`/`ModeToggle` (system resolution via mocked `matchMedia`, `.dark` class toggles, localStorage persisted/rehydrated); dashboard filtering (list reflects `?status=` param).
- **Mocks/boundaries:** MSW for `listRuns` and workflow endpoints (existing handlers). Mock `window.matchMedia`. Add shared jsdom shims for Radix `Select`: `Element.prototype.hasPointerCapture`, `Element.prototype.scrollIntoView`, `ResizeObserver` (ADR-005).
- **Critical scenarios / edge cases:** custom-IDE option round-trips through shadcn `Select`; empty/loading/error/no-cwd dashboard states render with skeletons/empty states; cards with zero counts still render (layout stability); narrow-viewport card wrap (where assertable).

### Integration Tests

- **Components together:** Router + dashboard (App-level tests in `__tests__/`): clicking a status card updates the URL and filters the rendered rows; the shell renders nav + daemon status + cwd switcher after the `sidebar-07` swap; form submit flows (start-run, workflow create/edit) still navigate and invalidate queries after the Select swap.
- **Test data/setup:** Existing MSW handlers and route-render helpers; no new fixtures beyond a runs array spanning all five statuses for the cards/filter tests.
- **Environment:** jsdom with the added Select shims and `matchMedia` mock in the shared Vitest setup file.

## Development Sequencing

### Build Order

Fixed sequence from ADR-001; each step lands green (`bun test` + `bun run typecheck`) before the next.

1. **Status tokens + `StatusBadge`** (F1) — no dependencies. Add tokens to `index.css`; add `card`/`badge`/`skeleton`/`table` primitives via CLI as needed; build and unit-test `StatusBadge`.
2. **App shell `sidebar-07`** (F2) — depends on 1 (uses theme-ready tokens; not strictly required but sequenced here). Add `sidebar` primitive; swap `AppShell` structure; preserve nav/`DaemonStatus`/`CwdSwitcher` and shell testids.
3. **Runs list → shadcn `Table`** (F3) — depends on 1 (`StatusBadge`) and 2 (renders inside new shell). Icon-first rows; carry all row testids/roles forward.
4. **Status summary cards + URL filter** (F4) — depends on 1 (`StatusBadge`) and 3 (filters that list); add `validateSearch` to `indexRoute`; cards `navigate` the `status` param.
5. **Remaining features → shadcn** (F5), one bounded PR each, all depend on 1 and 2:
   - 5a. Start-run form — re-skin + workflow `Select` (ADR-005).
   - 5b. Workflow editor + `StepFields`/`EdgesField` — re-skin (keep RHF/zod) + `ide`/`mode` `Select` via `Controller` (ADR-005); preserve custom-IDE round-trip.
   - 5c. Workflows list — re-skin to `Table`/`Card`.
   - 5d. Run view — banners→`Alert`, controls→`Button`, summary→`Card`.
6. **Theme selector + polish** (F6) — depends on 1 (tokens themed for both modes) and 2 (`ModeToggle` in shell header). Add `ThemeProvider` in `main.tsx`; `ModeToggle`; loading skeletons + action-oriented empty states across primary views.

### Technical Dependencies

- **Network access during build PRs** for the shadcn CLI to fetch primitives and install Radix peers (ADR-001). If unavailable, fall back to hand-authoring the specific primitive (documented alternative in ADR-001).
- **No infra/external-service or team dependencies** — all work is within `web/`.

## Monitoring and Observability

Not applicable as a runtime concern — this is a local-first dev-tool SPA with no telemetry. "Observability" here is the **test suite + typecheck** acting as the per-PR gate, plus the manual verification checks tied to PRD KPIs (5-second glance, ≤2-click triage, light/dark legibility of every `StatusBadge` state). Each migration PR must show `bun test` green and `bun run typecheck` clean before merge.

## Technical Considerations

### Key Decisions

- **Decision:** Source primitives via the shadcn CLI. **Rationale:** canonical, matches existing `components.json`, auto-installs Radix peers. **Trade-off:** build-time network dependency. **Alternatives rejected:** hand-authoring (more upkeep, drift risk) — kept as offline fallback. (ADR-001)
- **Decision:** Build `StatusBadge` + tokens first. **Rationale:** quarantine the one volatile, test-coupled piece so every later feature consumes a stable primitive. **Trade-off:** none material. **Alternatives rejected:** inline status styling per component (perpetuates `statusClass()` scatter).
- **Decision:** Dashboard filter via typed URL search param. **Rationale:** shareable/persistent, router-idiomatic, zero new data. **Trade-off:** a `validateSearch` parser to maintain. **Alternatives rejected:** local `useState` (not persistent), Zustand (over-scoped). (ADR-003)
- **Decision:** Hand-rolled theme provider. **Rationale:** ~40 lines, no dep, `.dark` CSS already present, easily testable. **Trade-off:** we maintain the system-listener/hydration code. **Alternatives rejected:** `next-themes` (Next-oriented dep for a Vite SPA). (ADR-004)
- **Decision:** Radix shadcn `Select` everywhere. **Rationale:** full visual consistency. **Trade-off:** DOM/interaction-model change → `Controller` wiring for `ide`/`mode`, test rewrites, jsdom shims. **Alternatives rejected:** native styled `<select>` (less consistent), mixed (two patterns). (ADR-005)

### Known Risks

- **Silent test breakage across the 19-file suite** (`run-row-${id}`, `getByRole('table')`, `aria-pressed`, `getByLabelText`, form testids). *Likelihood: high.* *Mitigation:* `StatusBadge` first; carry every selector forward; deliberate selector audit per PR; suite is the gate.
- **Radix `Select` + jsdom friction** (missing pointer/scroll APIs, portalled content, `register` incompatibility). *Likelihood: high.* *Mitigation:* shared setup shims; move `ide`/`mode` to `Controller`; drive options by click/keyboard and query by `role="option"`/text. (ADR-005)
- **`sidebar-07` fighting existing router/store wiring.** *Likelihood: medium.* *Mitigation:* thin structural swap only; do not refactor `CwdSwitcher`/`DaemonStatus`/form internals in the shell PR (ADR-001).
- **Theme flash-of-wrong-mode on first paint.** *Likelihood: low-medium.* *Mitigation:* apply persisted theme synchronously in the provider initializer; add a tiny pre-hydration inline script only if a flash is observed (ADR-004).
- **Rewrite-trap / never finishing** (the council's central concern). *Likelihood: medium.* *Mitigation:* fixed per-feature PR order, each green; no big-bang branch (ADR-001).
- **Five cards crowding narrow viewports.** *Likelihood: low.* *Mitigation:* responsive grid that wraps; count+label legible at all widths (ADR-002).
