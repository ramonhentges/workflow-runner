# ADR-006: react-hook-form + zod for the step editor; web `workflows` feature module

## Status

Accepted

## Date

2026-06-03

## Context

The step editor is a deeply nested form: an ordered list of steps, each with
scalar fields (id, ide, agent, model, mode, description) and a nested list of
edges (target step + intent), with add/remove/reorder at both levels and
per-field validation before save (PRD, ADR-004). The existing `StartRunForm`
uses plain `useState`, which is fine for a flat two-field form but becomes heavy
hand-wiring for dynamic nested arrays and field-level errors. `zod` v4 is already
a web dependency; `react-hook-form` is not.

## Decision

Adopt **react-hook-form** (with `useFieldArray` for the steps and per-step edges
arrays) plus a **zod resolver** over a shared `WorkflowDraftSchema`, for the
workflow create/edit form only. Place all new UI in a new feature module
`web/src/features/workflows/` (list, editor, step row, edges sub-form, agent/model
picker, hooks), with API access added to `web/src/lib/api/client.ts` and wire
types to `web/src/lib/api/types.ts`. Add routes `/workflows`, `/workflows/new`,
and `/workflows/$name/edit` to `router.tsx`, and a "Workflows" nav link in
`AppShell`. The agent/model picker is a combobox backed by the catalog query
(ADR-005) that always permits free-text entry.

The zod schema mirrors the server's domain validation (ADR-004) for instant
feedback; the server remains the source of truth.

## Alternatives Considered

### Alternative 1: Plain useState + zod (no new dependency)

- **Description**: Manage nested step/edge state with `useState` like `StartRunForm`; validate with zod on submit.
- **Pros**: No new dependency; one form paradigm in the codebase.
- **Cons**: Significant manual wiring for add/remove/reorder and per-field error mapping across nested arrays; more bug surface.
- **Why rejected**: The form's nesting is exactly what `useFieldArray` exists for; the wiring cost outweighs avoiding one well-established dependency.

### Alternative 2: A heavier form/runtime framework (e.g. TanStack Form)

- **Description**: Adopt a different form library.
- **Cons**: Less ubiquitous here; no advantage over react-hook-form for this shape.
- **Why rejected**: react-hook-form + zod is the most conventional, lowest-surprise choice.

## Consequences

### Positive

- `useFieldArray` handles dynamic step/edge arrays and reordering with minimal code; zod resolver gives structured per-field errors.
- New code is isolated in a `workflows` feature module, matching the existing `features/*` layout.

### Negative

- Introduces a second form paradigm alongside `StartRunForm` (plain useState) until/if that is migrated.
- One new runtime dependency to maintain.

### Risks

- Schema drift between the web zod schema and server domain validation. *Mitigation:* keep the web schema deliberately minimal and treat 400 `WORKFLOW_INVALID` from the server as authoritative; cover with tests.

## Implementation Notes

- Add `react-hook-form` (and `@hookform/resolvers` for the zod resolver) to `web/package.json`.
- Reuse existing shadcn `Input`/`Label`/`Button`; add `select`/`combobox` as needed.
- Catalog fetch via a `useIdeCatalog(ide)` TanStack Query hook, enabled when an IDE is chosen; debounced/lazy to avoid spawning on every keystroke.
