# ADR-005: In-process Hono listener at a fixed loopback port with a discovery file

## Status

Accepted

## Date

2026-05-29

## Context

ADR-001 chose Hono + Zod, in-process, localhost-only, with a fixed port "configurable via
daemon flag." Two implementation questions remained:

1. **How the listener is mounted.** The daemon today binds only a Unix domain socket
   (`bindSocket` in `src/infra/daemon/daemon.ts`) and serves JSON-RPC per connection. The new
   HTTP/WS listener must coexist in the same process and event loop without starving the UDS
   surface, and shut down cleanly.
2. **How a consumer discovers the port.** The future UI has no shell context and must find the
   API's TCP port even when an operator overrides the default. The UDS path is derived from the
   storage root today; the TCP port needs an equivalent discovery mechanism.

## Decision

**Mount an in-process Hono server on `Bun.serve` bound to IPv4 loopback at a fixed default
port (4517), overridable by flag/env, and write the actual bound port to a discovery file in
the storage root.**

- **Runtime**: Hono with the Bun adapter; HTTP routes via `@hono/zod-openapi`, WebSocket via
  `hono/bun`'s `createBunWebSocket` (Bun's native `Bun.serve` WebSocket). One `Bun.serve`
  instance for both HTTP and WS.
- **Bind**: explicit `hostname: "127.0.0.1"` (IPv4 loopback only). After listen, assert the
  bound address is `127.0.0.1` and is not `::`/`0.0.0.0`; a non-loopback bind aborts daemon
  startup (ADR-001 security baseline).
- **Port**: default `4517`; overridable by `--api-port` flag and/or `WORKFLOW_RUNNER_API_PORT`
  env. On successful bind, write `{ pid, apiPort, socket }` to `daemon.json` in the storage root
  (`0600`), removed on shutdown alongside the lockfile/socket.
- **Coexistence**: the listener starts after `RunManager.discoverOnStartup()` and after the UDS
  bind, inside the existing `runDaemon` flow. Bun's event loop multiplexes both; the
  N-idle-connections latency test (ADR-001) guards against starvation.
- **Shutdown**: `makeShutdown` is extended to drain WS clients (send close frame, brief grace
  period) and `server.stop()` the Hono listener **before** `runManager.shutdown()` and removing
  the socket/lockfile/discovery file.

## Alternatives Considered

### Alternative 1: Fixed default port, flag-overridable, no discovery file

- **Description**: Default `4517` + flag/env; consumers hardcode the default.
- **Pros**: Simplest; no extra file.
- **Cons**: A UI breaks silently when an operator overrides the port; no programmatic way to
  find the live port.
- **Why rejected**: The primary consumer (a future UI) needs reliable discovery; the file is
  cheap and mirrors the existing socket/lockfile pattern.

### Alternative 2: Ephemeral port (bind 0) + mandatory discovery file

- **Description**: OS picks a free port every start; always written to the discovery file.
- **Pros**: No port-collision configuration ever.
- **Cons**: The port changes each restart; the file becomes mandatory to read for any access,
  including ad-hoc `curl`; harder manual testing and docs.
- **Why rejected**: A stable, documentable default is friendlier for manual use and docs; the
  discovery file already covers the override case, giving the best of both.

### Alternative 3: Separate gateway process owning the HTTP/WS listener

- **Description**: A second process bridges HTTP/WS to the daemon's UDS.
- **Pros**: Listener crash can't take down the CLI/TUI; process isolation.
- **Cons**: Two processes/supervisors/logs for a single-maintainer tool; extra round-trip.
- **Why rejected**: Already rejected in ADR-001; in-process is the V1 choice.

## Consequences

### Positive

- A UI reads `daemon.json` to find the live port regardless of overrides — robust discovery.
- One `Bun.serve` instance, one bind assertion, one shutdown drain to reason about.
- Stable default port keeps manual `curl`/docs simple.

### Negative

- The daemon process now owns a second listener; shutdown ordering and event-loop sharing
  must be deliberate (addressed in the shutdown sequence above).
- A new artifact (`daemon.json`) to create, secure (`0600`), and clean up.

### Risks

| Risk | Mitigation |
|---|---|
| HTTP/WS work starves the UDS JSON-RPC loop, hurting CLI/TUI latency | N-idle-WS-connections + p95 UDS latency integration test (ADR-001 KPI). |
| Port 4517 already in use on the host | Bind error aborts startup with a clear message; operator overrides via flag/env (written to the discovery file). |
| Discovery file goes stale after a crash | Written on bind, removed on graceful shutdown; consumers cross-check `pid` liveness as they already do for the lockfile. |
| Non-loopback bind via misconfiguration | Post-listen bind assertion aborts startup; DNS-rebinding falsification test in CI (ADR-001 F5). |

## Implementation Notes

- New module tree under `src/app/api/` (per ADR-001): Hono app, route handlers, WS upgrade
  handler, the `Host`/`Origin` allowlist middleware, and the bind/assert/discovery-file logic.
- `runDaemon` gains the API listener mount alongside `bindSocket`; `makeShutdown`'s
  `ShutdownDeps` gains the API server handle and the discovery-file path.
- Discovery file schema is a Zod type in the shared schema module so a consumer can validate it.
