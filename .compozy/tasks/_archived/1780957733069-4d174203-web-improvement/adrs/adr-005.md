# ADR-005: Adopt the Radix-backed shadcn Select for all dropdowns, with deliberate test adaptation

## Status

Accepted

## Date

2026-06-06

## Context

The forms use native `<select>` elements in three places: the start-run workflow picker, and each step's `ide` and `mode` fields in `StepFields`. (The agent/model fields are *not* selects — `AgentModelPicker` is an `<Input>` + `<datalist>` and is out of scope for this decision.) ADR-002 set a "visual-primitives-only" form-migration policy to minimize test churn. However, the user explicitly chose to adopt the Radix-backed shadcn `Select` everywhere for full visual consistency. Radix `Select` is not a native `<select>`: it renders a button trigger + portalled listbox, exposes `role="combobox"`/`role="option"`, and relies on pointer APIs (`hasPointerCapture`, `scrollIntoView`) that jsdom does not implement. The existing tests drive these controls with Testing Library's `selectOptions`, which only works on native `<select>`.

## Decision

Replace all native `<select>` elements with the shadcn `Select` (`SelectTrigger`/`SelectValue`/`SelectContent`/`SelectItem`). This is the one sanctioned exception to ADR-002's "visual-only, no DOM change" rule, made explicit here. Each Select swap is treated as its own selector-audit checkpoint within its feature PR:

- Preserve the field `id` on `SelectTrigger` and existing `data-testid`s (e.g. `step-ide-select-${i}`, `step-mode-select-${i}`) on the trigger.
- Preserve the `StepFields` custom-IDE behavior: when a loaded workflow carries an `ide` outside the four built-ins, render an extra `SelectItem` for that value so it round-trips on edit.
- Update affected tests to drive Radix `Select` (click trigger → click option, or `keyboard`) instead of `selectOptions`, and stub the jsdom-missing pointer APIs in test setup.

## Alternatives Considered

### Alternative 1: Keep native `<select>`, shadcn-styled (the ADR-002 default path)

- **Description**: Keep accessible native `<select>`/`<option>` elements, apply shadcn-consistent classes.
- **Pros**: Zero interaction-model change; existing `selectOptions` tests untouched; lowest churn.
- **Cons**: Dropdown visuals are not "true" shadcn.
- **Why rejected**: User chose full visual consistency over minimal churn for this control.

### Alternative 2: Mixed (Select for simple, native for complex)

- **Description**: shadcn Select for static option sets, native for others.
- **Pros**: Pragmatic.
- **Cons**: Two patterns for the same control type.
- **Why rejected**: Inconsistency is exactly what V1 aims to remove.

## Consequences

### Positive

- All dropdowns share the shadcn look and keyboard/focus behavior.
- Eliminates the last native-control visual seam in the forms.

### Negative

- Adds a `@radix-ui/react-select` peer dependency (installed by the shadcn CLI).
- Form tests that used `selectOptions` must be rewritten; test setup must stub `hasPointerCapture`/`scrollIntoView`.

### Risks

- **jsdom + Radix Select friction** — pointer/scroll APIs missing; portalled content. *Likelihood: high.* *Mitigation*: add a shared test-setup shim (`Element.prototype.hasPointerCapture`, `scrollIntoView`, `ResizeObserver`) once; drive options via click/keyboard; query by `role="option"`/visible text. Audit per form PR; the suite stays the gate.
- **`register()` incompatibility** — Radix `Select` is not an input `register` can bind to. *Mitigation*: wrap each Select in a react-hook-form `Controller` (the `ide`/`mode` fields move from `register` to `Controller`, mirroring how `agent`/`model` already use `Controller`). This is a wiring change confined to those two fields, not a broader form rewrite.

## Implementation Notes

The `ide` and `mode` fields switch from `{...register(...)}` to a `Controller` + `Select` (`value`/`onValueChange`). The start-run picker switches its local-state `<select>` to `Select` with `value`/`onValueChange`. Shared jsdom shims live in the existing Vitest setup file. Each change lands in its feature PR (start-run form PR; workflow editor PR) and must leave `bun test` green.
