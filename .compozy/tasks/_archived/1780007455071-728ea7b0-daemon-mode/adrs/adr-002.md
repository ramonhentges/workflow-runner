# ADR-002: Terminal-Multiplexer Mental Model for the Daemon CLI

## Status

Accepted

## Date

2026-05-25

## Context

ADR-001 settled the V1 *scope* of daemon mode (parallel runs, attach/detach, CLI message queue, `retry-step`, daemon-restart discovery). It did not settle the *mental model* the product presents to the user — which dictates command names, defaults, error messages, the shape of `ps` output, and what feels native vs awkward.

Three coherent shapes are viable:

- A terminal-multiplexer model (tmux/abduco-shaped), where each run is a "session" you attach to and detach from, and the daemon is invisible plumbing.
- A process-supervisor model (pm2/supervisord-shaped), where each run is a managed process and the TUI is one of several views onto it.
- A two-mode CLI that preserves today's foreground behavior unchanged and adds daemon-mode behind explicit verbs.

Six PRD-level UX decisions had already been made by the user before this choice: `start` auto-attaches docker-run-style; completion signal is daemon-log + `ps` history of terminal-state runs; run ids are short-id + auto-generated two-word slug with prefix matching; detach is via a `/detach` slash command; multi-attach is broadcast; `stop` is graceful-then-forceful producing an `aborted` status. All six lean strongly toward the multiplexer model — `/detach`, auto-attach, slug-style ids, and broadcast multi-attach are tmux idioms, not pm2 idioms.

Market research independently confirmed the same pull: developers in the target audience (solo CLI-native devs running long agent sessions) already use tmux/screen/zellij daily; pm2's user-reported pain points (`save`/`resurrect` confusion, restart-counter quirks, opaque startup scripts) suggest the process-supervisor model invites incidental complexity that doesn't pay off for a single-user tool.

## Decision

The `workflow-runner` daemon CLI will be designed around a **terminal-multiplexer mental model**:

- A *run* is treated as a *session*: a long-lived thing the user attaches to, detaches from, and re-attaches to.
- `attach`/`detach` are first-class verbs; the slash command `/detach` is the in-TUI detach mechanism (Ctrl-C kills the TUI, as users expect).
- `start <workflow>` auto-attaches by default; `--detach`/`-d` starts in the background.
- `ps` is "list sessions" — narrow, scannable, with humanized elapsed time and a marker glyph for "TUI currently attached."
- The daemon is invisible plumbing: auto-spawned on first CLI invocation (gpg-agent style), with a single stderr line on first spawn and a silent socket-discovery path thereafter.
- Run identifiers are short-id + two-word slug, both accepted with unambiguous prefix matching (Docker-style).
- Multi-attach is broadcast: multiple TUIs may observe the same run; input handling between them is a separate design point (see Open Questions in the PRD).

## Alternatives Considered

### Alternative 1: Process-supervisor model (pm2-like)

- **Description**: Treat each run as a managed process. `start`/`stop`/`ps`/`logs` as the primary verbs. The TUI becomes a "tail and interact" tool rather than the canonical view of a run. Lifecycle is explicit; users routinely script against `ps` output.
- **Pros**: Familiar to devs already using pm2 / supervisord; explicit lifecycle is clearer for unattended/CI scenarios; scripting feels natural; aligns with the language ops teams already speak.
- **Cons**: Mismatch with the stated V1 persona (solo dev parallel agent supervision, not service fleet management); pm2's well-documented user pain (`save`/`resurrect` dance, restart-counter quirks) suggests the model invites incidental complexity; demotes the TUI from primary surface to afterthought, which conflicts with the user's explicit "attach/detach TUI" request.
- **Why rejected**: V1 persona is solo developer who already lives in tmux; mental-model fit favors the multiplexer model. The CI/unattended persona for which this approach excels is explicitly out of scope for V1.

### Alternative 2: Two-mode CLI (preserve today's foreground path, add daemon as opt-in)

- **Description**: Keep `workflow-runner <workflow.json>` foreground behavior unchanged for backwards-compatibility. Add `workflow-runner daemon start`, `workflow-runner run start <workflow.json>`, etc., behind explicit verbs. Both paths supported indefinitely.
- **Pros**: Zero migration risk; existing scripts and muscle memory keep working; allows in-the-wild A/B comparison of the two experiences.
- **Cons**: Doubles the user-facing surface (every feature has two ways to reach it); doubles the maintenance burden (every change has to be verified in two modes); the foreground path becomes legacy code competing with daemon-mode polish; in practice the foreground path will fall out of use within weeks, making the duplication pure cost.
- **Why rejected**: There is exactly one current user (the project author), so the backwards-compat argument carries no weight. The "extra surface for safety" cost is real and recurring; the safety it buys is theoretical.

## Consequences

### Positive

- Every command name, default, and error message has a clear unifying mental model to anchor against; reduces bikeshedding during PRD and techspec design.
- The six already-decided UX choices fall out of the model naturally — no contradictions, no special cases.
- Users in the target audience can productively use the tool with near-zero ramp-up because the model is already in their muscle memory.
- The daemon's auto-spawn becomes uncontroversial: in a multiplexer model, the "server" is expected to be invisible, just as `tmux server` is.

### Negative

- The terminal-multiplexer model is less natural for scripting; if a future use case requires headless scripted runs (e.g., CI invocation), the CLI may need new flags (`--json`, `--no-tty`) to suit it. This is acceptable for V1 but should be tracked.
- `ps` output as a scannable column view requires care to keep narrow on standard terminals (80 cols). Adding columns later will need explicit user-visible flags rather than silent expansion.

### Risks

- **Auto-attach surprises in non-TTY environments** (piped invocation, CI). Mitigation: detect non-TTY stdout and default to background mode automatically, printing the run-id for the script to capture.
- **Auto-spawn failure modes** (daemon binary missing, socket dir not writable). Mitigation: explicit, loud, actionable stderr; `doctor` subcommand for diagnosing.
- **Confusion between "killing the TUI" and "stopping the run"**. Mitigation: Ctrl-C in the TUI always kills the TUI only (matching tmux), and the TUI displays a brief "run still alive — `attach` to return" banner on exit. Stopping the run requires explicit `stop <run-id>`.

## Implementation Notes

This ADR is mental-model-level and intentionally non-prescriptive about code. The PRD operationalizes it into concrete commands, behaviors, and success criteria; the techspec maps it onto Bun/UDS/JSONL implementation details. Implementers should treat any deviation from the multiplexer model as a flag worth raising rather than a silent design drift.
