# ADR-004: Hand-rolled theme provider over a next-themes dependency

## Status

Accepted

## Date

2026-06-06

## Context

PRD feature F6 requires a system/light/dark theme selector with browser-local persistence (ADR-002). `index.css` already defines `:root` and `.dark` token blocks and a `@custom-variant dark (&:is(.dark *))`, so the rendering side is class-driven and complete — only the *control* (resolve system preference, toggle the `.dark` class, persist the choice) is missing. shadcn's documented default is `next-themes`, a library built primarily for Next.js. This is a Vite SPA with no SSR.

## Decision

Implement a small hand-rolled theme provider (`src/components/theme-provider.tsx`, ~40 lines): a React context exposing `{ theme, setTheme }` where `theme` is `'system' | 'light' | 'dark'`. It resolves the effective theme (using `matchMedia('(prefers-color-scheme: dark)')` when `system`), toggles the `.dark` class on `document.documentElement`, persists the choice to `localStorage('theme')`, and listens for system-preference changes while in `system` mode. A `ModeToggle` header control calls `setTheme`. The provider wraps `RouterProvider` in `main.tsx`.

## Alternatives Considered

### Alternative 1: Add the `next-themes` dependency

- **Description**: Use `next-themes` `<ThemeProvider attribute="class" defaultTheme="system" enableSystem>`.
- **Pros**: Handles system sync, persistence, and SSR flash-of-unstyled-content out of the box; less code.
- **Cons**: Pulls a Next.js-oriented dependency into a Vite SPA for a need that is ~40 lines; the SSR flash logic it carries is irrelevant here.
- **Why rejected**: YAGNI / dependency minimization — the class-and-localStorage strategy is small, fully covered by the existing `.dark` CSS, and trivially testable in the existing Vitest/jsdom setup.

## Consequences

### Positive

- Zero new runtime dependencies.
- Directly testable with Vitest/jsdom (mock `matchMedia` + `localStorage`).
- Full control over the exact `theme` model and persistence key.

### Negative

- We own ~40 lines that `next-themes` would otherwise maintain (system-change listener, hydration read).

### Risks

- **Flash of wrong theme on first paint** before React mounts. *Mitigation*: read `localStorage` and apply the `.dark` class synchronously in the provider's initializer (and optionally a tiny inline pre-hydration script in `index.html` if a flash is observed); acceptable for a local-first dev tool.
- **`matchMedia` absent in jsdom.** *Mitigation*: tests mock `window.matchMedia`; the provider guards for its absence.

## Implementation Notes

Provider mounts in `main.tsx` outside `RouterProvider`. `localStorage` key: `theme`. Effective-theme resolution: `theme === 'system' ? matchMedia(...) : theme`. The toggle is placed in the new shadcn sidebar/header (F2).
