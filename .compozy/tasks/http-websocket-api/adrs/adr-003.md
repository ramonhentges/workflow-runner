# ADR-003: RunManager is the shared application service (no new seam module)

## Status

Accepted

## Date

2026-05-29

## Context

ADR-001 set the architecture as "a transport-agnostic application-service layer that both
the existing JSON-RPC server and the new HTTP/WS server consume," and its implementation
notes proposed extracting a new `src/domain/app-service.ts` module that orchestrates
`RunManager` + `EventLog`, with the JSON-RPC handlers refactored to delegate to it.

Inspecting the code surfaced a conflict and a redundancy:

- **Domain purity.** `CLAUDE.md` requires `src/domain/` to be I/O-free. An app-service that
  orchestrates `RunManager` and `EventLog` necessarily depends on infra types
  (`EventLogEntry`, `RunSnapshot`, the `McpServer`-backed runner lifecycle). Placing it in
  `domain/` would violate that rule.
- **Redundancy.** `RunManager` is *already* transport-agnostic. It exposes exactly the
  operations the seam needs — `startRun`, `list`, `get`, `retryStep`, `stop`, `sendInput`,
  `attachSubscriber`, `openEventLog` — and contains no JSON-RPC, HTTP, or socket concerns.
  The JSON-RPC handlers in `src/infra/daemon/handlers/*` are already thin adapters that parse
  wire params, call one `RunManager` method, and map errors. A new module wrapping
  `RunManager` would duplicate its surface for no behavioral gain.
- **The port rule.** `CLAUDE.md`: "A port interface is only needed when it has two or more
  implementations." `RunManager` has a single production implementation; introducing an
  interface in front of it (with only a test fake as a second impl) adds a type without
  earning it.

## Decision

**Treat `RunManager` itself as the shared, transport-agnostic application service. Do not
introduce a new seam module or a `RunService` interface.**

- The new HTTP route handlers and the WebSocket attach handler depend on `RunManager`
  directly, exactly as the JSON-RPC handlers already do.
- Each HTTP/WS handler stays thin: parse and validate wire input (Zod), call one
  `RunManager` method, map `RunManagerError` codes to the transport's error shape. No
  business logic in handlers.
- `RunManager` gains the small surface needed by the new transport but kept transport-neutral:
  `startRun(workflowPath, cwd)` (cwd threaded into `new Runner(..., { cwd })`); the
  retry-step and health operations are already present or trivially derivable (`list`,
  existing doctor inputs).
- The "no business logic in transport handlers" rule is enforced by the speciation-guard
  test from ADR-001 (a test-only stdin/stdout adapter must drive `RunManager` through the
  same thin-handler pattern) rather than by a structural interface boundary.

## Alternatives Considered

### Alternative 1: New `domain/app-service.ts` module (ADR-001's literal framing)

- **Description**: Extract a module that orchestrates `RunManager` + `EventLog`; both
  transports delegate to it.
- **Pros**: A single named "seam" symbol; matches ADR-001's wording.
- **Cons**: Violates the domain-purity rule if placed in `domain/`; duplicates `RunManager`'s
  already-transport-agnostic surface; most code churn for no behavioral benefit.
- **Why rejected**: Redundant given `RunManager` already is the seam; conflicts with
  `CLAUDE.md`.

### Alternative 2: Introduce a `RunService` port interface over `RunManager`

- **Description**: Define an interface capturing the operations; `RunManager` implements it;
  both transports depend on the interface.
- **Pros**: Compile-time guarantee that handlers touch only the agreed surface; cleaner
  speciation story.
- **Cons**: Single production implementation violates the project's port rule (interface only
  when 2+ implementations); the speciation guard already covers drift via a test adapter.
- **Why rejected**: Adds an abstraction the port rule does not justify; YAGNI.

## Consequences

### Positive

- Smallest possible change: no new module, no new interface, no refactor of the existing
  JSON-RPC handlers beyond the `startRun` cwd parameter.
- One source of operation truth (`RunManager`) for all transports; new verbs are added once.
- Consistent with the existing handler pattern, so the codebase reads uniformly.

### Negative

- The "seam" is a convention (thin handlers + `RunManager`) rather than a compile-time
  boundary; nothing structurally prevents a handler from growing business logic.

### Risks

| Risk | Mitigation |
|---|---|
| A future handler embeds business logic, re-introducing the speciation risk the Thinker flagged | Speciation-guard test (ADR-001 F8): a test-only stdin/stdout adapter drives `RunManager` with no `RunManager` changes; code review enforces thin handlers. |
| `RunManager` accretes transport-specific concerns over time | Keep all wire parsing/validation/error-mapping in the per-transport handlers; `RunManager` methods take and return plain domain/infra values only. |

## Implementation Notes

- `RunManager.startRun` signature becomes `startRun(workflowPath: string, cwd: string)`; the
  cwd is passed to `new Runner(workflow, factory, mcp, { cwd, onStepBoundary })` (Runner
  already accepts `opts.cwd`, currently defaulting to `process.cwd()`).
- The JSON-RPC `run.start` params gain `cwd`; the CLI client populates it from its own
  `process.cwd()` so existing CLI behavior is preserved.
- For the same domain-purity reason, the shared Zod schemas live in the API adapter
  (`src/app/api/schema.ts`), **not** in `src/domain/`. ADR-001's implementation note placing
  them at `domain/api-schema.ts` is superseded: they are transport/wire shapes, not domain
  entities.
