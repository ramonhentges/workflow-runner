# ADR-004: Serve the web UI from its own origin; admit it via an env-gated allowlist + CORS

## Status

Accepted

## Date

2026-05-31

## Context

The daemon API is loopback-only and enforces two browser-facing guards in
`src/app/api/security.ts`: a `Host`-header allowlist on all HTTP routes and an
`Origin` allowlist on WebSocket upgrades, both accepting only
`127.0.0.1:<port>` / `localhost:<port>`. The web UI runs from its own dev/static
server on a different port, so its browser Origin will not match, and
cross-origin `fetch` to the API would additionally be blocked by CORS (the API
sends no CORS headers today).

## Decision

Run the web UI from its own server and **extend the daemon's security layer to
admit the UI origin**, gated by an environment variable
(`WORKFLOW_RUNNER_UI_ORIGIN`, e.g. `http://localhost:5173`). Specifically:

- `isOriginAllowed` additionally accepts the configured UI origin for WS
  upgrades.
- Add CORS response headers (origin-reflected for the configured UI origin,
  with credentials disabled) to the HTTP API so cross-origin `fetch` succeeds.
- The `Host` allowlist is unchanged: cross-origin requests still target the API
  host, which already passes.

When the env var is unset, behaviour is identical to today (no widening), so
production deployments that do not run the separate UI are unaffected.

The browser learns the API base URL from a Vite build/dev env var
(`VITE_API_BASE_URL`, default `http://127.0.0.1:4517`) rather than reading the
daemon's `daemon.json` discovery file, which a browser cannot access.

## Alternatives Considered

### Alternative 1: Daemon serves the built UI on its own port (same origin)

- **Description**: Compile the UI and serve it from the daemon so Origin/Host
  match with no security change.
- **Pros**: No security widening in production; zero CORS.
- **Cons**: Couples UI delivery to the daemon; dev still needs a proxy + origin
  exception; more build/packaging work.
- **Why rejected**: User chose the separate-server model for simpler operation.

### Alternative 2: Permanently hardcode an extra allowed origin

- **Description**: Bake a fixed extra origin into the allowlist.
- **Pros**: No configuration.
- **Cons**: Permanently widens the security surface even when the UI is not in
  use; inflexible port.
- **Why rejected**: Env-gating keeps the default posture closed.

## Consequences

### Positive

- UI and daemon evolve independently; simple to run in development.
- Security surface only widens when explicitly opted in via env var.

### Negative

- Adds CORS handling and an origin branch to the daemon's security code.
- Operators must set `WORKFLOW_RUNNER_UI_ORIGIN` (and `VITE_API_BASE_URL`)
  consistently.

### Risks

- Misconfiguration (mismatched ports) yields opaque CORS/WS failures.
  *Mitigation*: document the two env vars together; default the API base URL to
  4517.

## Implementation Notes

Changes live in `src/app/api/security.ts` (origin check + a CORS middleware,
wired in `app.ts`) and the WS pre-upgrade Origin check in
`routes/ws-attach.ts`. No change to the loopback bind address.
