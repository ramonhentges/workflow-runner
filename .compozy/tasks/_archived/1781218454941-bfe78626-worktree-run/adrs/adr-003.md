# ADR-003: Place isolated worktrees adjacent to the repository

## Status

Accepted

## Date

2026-06-11

## Context

An isolated run executes in a git worktree that must live somewhere on disk. The location affects discoverability (where the user looks for the work), repo cleanliness (whether the worktree pollutes the tracked tree), and the risk of agents/tools recursing into nested worktrees. This was an open question carried over from the PRD.

## Decision

Create the worktree **adjacent to the repository**: as a sibling of the repository root, named from the repository directory name and a filesystem-sanitized form of the branch — e.g. for repo `/work/app` on branch `feat/x`, the worktree path is `/work/app-feat-x`. The repository root is resolved with git (`resolveRepoRoot`), not assumed to equal the run's `cwd`, so a `cwd` inside a subdirectory still produces a sibling of the true repo root. The resolved `worktreePath` is persisted in the run snapshot and surfaced to the user.

## Alternatives Considered

### Alternative 1: Daemon-managed directory

- **Description**: Place worktrees under the daemon storage root, keyed by run id or branch.
- **Pros**: Centralized; never pollutes the repo's parent; easy to enumerate.
- **Cons**: Less discoverable in the user's normal project layout; path is far from the project.
- **Why rejected**: User preferred worktrees to sit visually near the project.

### Alternative 2: Inside the repo (gitignored)

- **Description**: Place under `<repo>/.worktrees/<branch>`.
- **Pros**: Self-contained within the project.
- **Cons**: Requires gitignore handling; nested worktrees risk agents/tools scanning into them.
- **Why rejected**: Added nesting and ignore-management complexity.

## Consequences

### Positive

- Worktrees appear next to the project, matching a common developer convention.
- No in-repo nesting; no gitignore changes.

### Negative

- The repository's parent directory accumulates sibling worktree directories.
- Branch names must be sanitized into safe directory names, and two branches that sanitize to the same name would collide.

### Risks

- A computed worktree path may already exist (prior run, manual creation). Mitigation: `addWorktree` fails on an existing path and `RunManager` maps it to a worktree-conflict error rather than reusing or overwriting it.

## Implementation Notes

Path = `join(dirname(repoRoot), `${basename(repoRoot)}-${sanitize(branch)}`)`. `sanitize` replaces path separators and unsafe characters; the exact rule is specified in the TechSpec.
