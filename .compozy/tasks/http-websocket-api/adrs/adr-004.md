# ADR-004: Lean, attach-scoped WebSocket frame envelope

## Status

Accepted

## Date

2026-05-29

## Context

The PRD left open the WS subprotocol shape: should each WS frame mirror the internal
JSON-RPC notification envelope (`{method: "event.run.event", params: {runId, entry}}`) or use
a leaner shape scoped to the single attached run?

The WebSocket endpoint is `WS /runs/:id/attach` — already bound to one run for its entire
lifetime. The existing JSON-RPC notifications carry `runId` because a single UDS connection
multiplexes notifications for any run the client attaches to; that multiplexing does not exist
on a per-run WS connection. The event payload itself (`EventLogEntry`) is identical regardless
of envelope choice, so this decision is purely about the wrapper and the public contract a
future UI generates types from.

## Decision

**Use a lean, attach-scoped frame envelope owned by the public API, not the internal RPC
method names.** `runId` is implicit from the connection path and is not repeated in frames.

Server → client frames (discriminated by `type`):

- `{ type: "snapshot", snapshot: RunDetail }` — sent once on connect.
- `{ type: "backlog", entries: RunEvent[], truncated: boolean }` — replayed history on connect/resume.
- `{ type: "event", entry: RunEvent }` — one live event.
- `{ type: "status", status: RunStatus }` — run status transition.
- `{ type: "error", code: string, message: string }` — terminal protocol/usage error before close.

Client → server frames:

- `{ type: "input", message: string }` — chat-style input for an interactive step.

`RunEvent` is the Zod-validated shape of `EventLogEntry` (`seq`, `ts`, `stepId`, `event`).
Resume is carried as a query parameter on the upgrade (`?fromSeq=N`), not as a frame.
The frame set is documented in `docs/ws-protocol.md` (~30 lines) per ADR-001.

## Alternatives Considered

### Alternative 1: JSON-RPC-parity envelope

- **Description**: Frames mirror the existing notifications verbatim, e.g.
  `{method: "event.run.event", params: {runId, entry}}` and
  `{method: "event.run.statusChanged", params: {runId, status}}`.
- **Pros**: The round-trip/speciation guard becomes trivial — one encoder for both transports;
  no second shape to maintain.
- **Cons**: Couples the public WS contract to internal RPC method naming (renaming an internal
  method becomes a breaking API change); ships a redundant `runId` on every frame; offers a UI
  a more awkward, method-string-keyed surface than a `type`-discriminated union.
- **Why rejected**: The connection is already run-scoped, so `runId` is noise, and binding the
  public contract to internal names is exactly the speciation coupling ADR-001 warns about. The
  shared **payload** (`RunEvent` via Zod) already gives the round-trip guard its teeth; the
  envelope need not match.

## Consequences

### Positive

- Clean, `type`-discriminated public contract that a UI can model directly and exhaustively.
- The public WS shape can evolve independently of internal JSON-RPC method names.
- No redundant `runId` on the hot path (every event frame).

### Negative

- Two envelope shapes exist (JSON-RPC notifications vs WS frames), so the conformance test must
  assert on the shared **payload** (`RunEvent`) rather than on byte-identical frames.

### Risks

| Risk | Mitigation |
|---|---|
| Payload drift between the JSON-RPC `entry` and the WS `entry` despite different envelopes | Both encode the same Zod `RunEvent` schema (single source of truth); the round-trip conformance test (ADR-001 F7) replays a recorded log through `RunEvent` and re-renders via the TUI parser. |
| `fromSeq`-on-upgrade resume re-introduces the gap-closing race in WS form | Reuse the exact backlog-then-gap-read ordering already proven in `run-attach.ts`; re-verify against the WS lifecycle (close codes, reconnect) per ADR-001's risk register. |

## Implementation Notes

- The WS attach handler reuses `RunManager.attachSubscriber` and the
  backlog → register-subscriber → flush → gap-read sequence from
  `src/infra/daemon/handlers/run-attach.ts`, emitting the lean frames instead of `ctx.notify`.
- `?fromSeq=N` maps directly to `EventLog.readEventsSince(N)`; `truncated` from
  `ReadEventsSinceResult` populates the `backlog` frame's `truncated` flag.
- Outbound frames are JSON text frames; a bounded send buffer closes the socket on overflow
  (ADR-001 operational guardrails).
