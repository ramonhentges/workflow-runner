# ADR-001: Step-sequenced TUI runner as the workflow execution model

## Status

Accepted

## Date

2026-05-22

## Context

The project must turn the existing single-session ACP client (`src/index.ts`) into
a runner that executes a multi-step workflow defined by a JSON config (e.g.
`workflows/who-is.json`). Each step names an agent persona, a model, and an
execution mode (`interactive` or `autonomous`), and declares outgoing `edges`
with natural-language `intent` descriptions. Each step must run in a fresh
connection and session.

The product question is what shape the runner should take so it serves both
modes well: interactive steps are a two-way conversation between the user and the
agent, while autonomous steps run the agent's work while streaming its thinking
and data to the terminal. The decision affects scope, reuse of existing code, and
the user experience of observing a run.

## Decision

Build the runner as a **step-sequenced TUI runner**: a single persistent
terminal UI that lives for the whole workflow run. The runner advances through
steps one at a time; for each step it spawns a fresh connection and session bound
to that step's agent, model, and mode. A step banner separates steps in one
shared scrollable log. Interactive steps show the input field for user chat;
autonomous steps hide the input and stream the agent's thinking and tool data
live. Every step's session is given two MCP tools — `handoff` (choose the next
step from the declared edges) and `finish` (end the workflow). Failures halt the
run and report; the run ends with an in-TUI summary and the TUI stays open.

## Alternatives Considered

### Alternative 1: Headless streaming console runner

- **Description**: Drop the TUI; print step banners, agent thinking, and tool
  data to stdout like a CI log. Interactive steps fall back to a raw stdin
  prompt only when needed.
- **Pros**: Trivial to log, replay, and pipe; simplest rendering; no UI library
  surface to maintain.
- **Cons**: Weakens the interactive-mode experience, which is a stated core
  requirement; discards the working TUI in `src/index.ts`.
- **Why rejected**: Interactive mode is a first-class requirement, and a raw
  stdin prompt is a visibly worse experience than the existing TUI input.

### Alternative 2: Workflow IDE / dashboard

- **Description**: A multi-pane TUI with a live graph view of nodes and edges,
  the current step highlighted, plus a step inspector and per-step log panes.
- **Pros**: Best for understanding and debugging complex workflow graphs;
  strongest situational awareness during a run.
- **Cons**: Large UI scope; multi-pane layout, graph rendering, and inspector
  are far more work than the MVP needs.
- **Why rejected**: Violates YAGNI for the MVP. The graph view is a desirable
  later enhancement, not a launch requirement.

## Consequences

### Positive

- Reuses the existing TUI, streaming, permission, and file-handler code in
  `src/index.ts`, reducing build effort.
- One shared log gives the user a continuous, readable narrative of the whole
  run across both modes.
- Cleanly expresses the interactive/autonomous distinction through input-field
  visibility, with no separate rendering path.

### Negative

- A single-pane log can grow long on large workflows; mitigated by step banners
  and scrollback.
- No visual graph of the workflow; the user reasons about routing from banners
  and edge intents rather than a diagram.

### Risks

- Spawning a fresh subprocess and session per step adds per-step startup
  latency. Mitigation: show a clear "starting step" status so the wait is
  legible; revisit pooling only if latency proves painful.
- Long runs accumulate log content in one scroll view. Mitigation: viewport
  culling is already enabled; step banners make navigation tractable.

## Implementation Notes

The runner extends `src/index.ts` rather than replacing it. The `handoff` and
`finish` MCP tools are exposed to each step's session via the `mcpServers`
declared at session creation. Step-to-step context transfer is limited to a
short handoff message (see PRD; future ADR may revisit).
