# ADR-004: Represent isolation as worktreePath + branch on the run snapshot

## Status

Accepted

## Date

2026-06-11

## Context

The `Run` aggregate and `RunSnapshot` already persist `cwd` — the directory the agent subprocess runs in — and round-trip it through snapshots (used by restart discovery and retry). Isolated runs need to (a) execute in the worktree rather than the user's chosen directory and (b) surface both the worktree path and branch wherever the run is displayed. We must decide how to model this in run state without breaking the non-isolated path.

## Decision

Keep `cwd` as the repository root the user selected. Add two optional fields to `RunSnapshot` (and the `Run` aggregate): `worktreePath?` and `branch?`. The runner executes in `worktreePath ?? cwd`, so non-isolated runs are byte-for-byte unchanged. The presence of `branch`/`worktreePath` marks a run as isolated. Both fields propagate through the snapshot, the RPC `RunListEntry`, the HTTP `RunSummary`/`RunDetail` schemas, and their renderers (CLI `ps`, web run detail).

## Alternatives Considered

### Alternative 1: Overwrite cwd, add only branch

- **Description**: Set `cwd` directly to the worktree path; add `branch`.
- **Pros**: Minimal change — everything downstream already reads `cwd`.
- **Cons**: The original repository root is lost from run state; harder to display both or reason about provenance.
- **Why rejected**: User wants both the repo root and worktree retained.

### Alternative 2: Single nested isolation object

- **Description**: Add `worktree: { path, branch, repoRoot }` to the snapshot.
- **Pros**: Groups isolation state.
- **Cons**: More nesting across the snapshot and every mirrored schema (RPC + HTTP + zod); larger diff.
- **Why rejected**: Two flat optional fields are simpler and match the existing flat-`cwd` style.

## Consequences

### Positive

- Non-isolated runs are unaffected (`worktreePath ?? cwd`).
- Both repo root and worktree are available for display and survive restarts/retry via the existing snapshot round-trip.
- Minimal, flat additions to existing schemas.

### Negative

- Two new optional fields must be threaded through every layer that mirrors the snapshot (domain, RPC protocol, HTTP zod schemas, renderers).

### Risks

- Schema drift between the RPC `RunListEntry`/`RunSnapshot` and the HTTP zod `RunSummary`/`RunDetail`. Mitigation: the existing conformance/openapi-completeness tests guard the HTTP surface; add field assertions.

## Implementation Notes

`Run.create` and `Run.fromSnapshot` accept the new optional fields; `snapshot()` emits them only when set (matching the existing conditional `cwd`/`endReason` handling). Retry (`Run.fromSnapshot` in `retryStep`) must carry them forward.
