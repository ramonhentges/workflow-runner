# ADR-003: One McpServer Instance Per Run

## Status

Accepted

## Date

2026-05-25

## Context

Today's `McpServer` (`src/infra/mcp/mcp-server.ts`) is single-step by construction: it holds `#currentStep`, `#currentResolve`, and `#currentStepToken` as instance fields, and `beginStep()` / `resetStep()` mutate that single slot. Daemon mode introduces concurrent runs, so the runtime must somehow serve multiple in-flight steps simultaneously.

Three viable options exist: (1) spawn a fresh `McpServer` instance per run on its own ephemeral port, keeping the single-step contract intact; (2) refactor the existing server into a multi-tenant dispatcher keyed by `(runId, stepId)`; (3) spawn the MCP server as a separate child process per run for full fault isolation.

The current single-step semantics tie the `StepToken` validation, the `handoff`/`finish` resolution, and the step-edge enforcement into one tightly-scoped piece of logic. Multi-tenant routing requires changing every one of those code paths to thread a routing key, and the failure modes (wrong run resolving the wrong step) are subtle. Per-run instances cost almost nothing — an HTTP server on `127.0.0.1:0` binds in single-digit milliseconds — and preserve the existing code path unchanged.

Separate-process MCP servers would harden against an MCP server bug taking down the daemon, but the MCP server today is ~400 lines of synchronous request dispatch with no known instability; spending IPC complexity for a hypothetical isolation gain is overkill at V1.

## Decision

Each `Run` owns one dedicated `McpServer` instance, spawned at run start and disposed at run end. The daemon's `RunManager` is responsible for the lifecycle. The existing `McpServer` class is reused verbatim — single-step semantics, `StepToken` validation, all unchanged. Per-run ports are auto-assigned by the kernel (`listen(0)`).

## Alternatives Considered

### Alternative 1: Single multi-tenant McpServer

- **Description**: One process-wide MCP server. `#currentStep`/`#currentResolve`/`#currentStepToken` become `Map<StepToken, {step, resolve}>`. Tool handlers look up the active step by the incoming `x-workflow-step-token` header (already in the protocol).
- **Pros**: Single port, single bind, marginally lower resource footprint.
- **Cons**: Every tool-call site changes; cross-run contamination risk if the dispatcher gets the routing key wrong; the existing `resetStep()` semantics no longer match (a reset for one run must not affect others); harder to reason about in tests.
- **Why rejected**: The benefit (one port instead of N) is negligible at V1 concurrency targets (≥4 runs); the cost (touching every tool dispatch path with routing logic) is real and recurring.

### Alternative 2: MCP server as separate child process per run

- **Description**: Daemon spawns each run's MCP server as a child process; tool calls are routed via IPC.
- **Pros**: Daemon crash doesn't take MCP servers down; full fault isolation; surprise crashes in MCP code can't take down sibling runs.
- **Cons**: Adds spawn overhead per run; needs an IPC channel between daemon and MCP server for `beginStep`/`resetStep`; doubles the supervised-process count; failure-mode complexity goes up faster than fault isolation pays back.
- **Why rejected**: The MCP server is small and has no observed crash history; the additional IPC complexity isn't justified for V1.

## Consequences

### Positive

- Existing `McpServer` code stays as-is; no refactor of the tool-call dispatch path.
- Single-step semantics are preserved per server, which matches how the rest of the code reasons about steps.
- Per-run logs of HTTP requests (if needed for debugging) are naturally isolated.
- A bug in MCP-server step-token handling affects only one run, not all running runs.

### Negative

- One HTTP server per active run consumes one ephemeral port + ~one event-loop pseudo-listener; on a machine with 4 concurrent runs this is invisible, on a machine with 50 it would become non-trivial. Not relevant for V1 targets.
- `RunManager` must own the lifecycle of N MCP servers, which adds bookkeeping in one place (the right place).

### Risks

- **Risk**: A run's `McpServer` is leaked (not closed on dispose) and accumulates port allocations. **Mitigation**: `Run` dispose path is a `try`/`finally` that always calls `McpServer.close()`; `doctor` reports orphan listening ports owned by the daemon process.
- **Risk**: The agent subprocess connects to the wrong MCP server URL (e.g., a stale URL from a previous run). **Mitigation**: The URL is passed fresh to the agent on spawn (already the case in `AcpAgentSessionFactory`); there is no shared registry to be stale against.

## Implementation Notes

The `RunManager.startRun()` method creates the `McpServer`, passes it to the `Runner` constructor as the `RunnerTools` implementation (unchanged interface), and stores both for later disposal. `Run.dispose()` calls `mcpServer.close()` then awaits the `Runner` to flush any pending event emission.
