# ADR-003: Thread scope through the existing workflow routes

## Status

Accepted

## Date

2026-06-10

## Context

ADR-001 calls for one combined, badged list of project and global workflows, and
full lifecycle parity for global workflows. Today the workflow API is a single
route tree keyed entirely off `?cwd=`: `GET /workflows` lists `<cwd>/workflows`,
and `GET/POST/PUT/DELETE /workflows/:name` resolve files under that directory by
bare name. `run.start` already accepts any absolute `workflowPath` plus any
`cwd`, so running a global workflow against the active project needs no run-layer
change. The open question is how to express **scope** across the list and CRUD
surface without splitting it into a parallel route tree.

## Decision

Extend the existing routes with a `scope` discriminator rather than adding
parallel `/global-workflows` endpoints:

- **List** — `GET /workflows?cwd=` returns project **and** global workflows
  merged server-side into one array. Each `WorkflowItem` gains a
  `scope: "global" | "project"` field. Global items are always included (they do
  not depend on `cwd`); project items require `cwd`.
- **CRUD** — `GET/POST/PUT/DELETE /workflows/:name` accept `?scope=global|project`,
  defaulting to `project` when omitted (back-compat). `scope=global` resolves the
  global directory (ADR-002) and ignores `cwd`; `scope=project` keeps the current
  `<cwd>/workflows` behavior.
- **Name uniqueness is per-scope.** A global and a project workflow may share a
  name; the `409` conflict check applies only within the target scope's
  directory. Operations are never ambiguous because scope is explicit.
- **Run-active guard** (`findActiveRunForWorkflow`) already matches by absolute
  file path, so it protects global delete/rename unchanged.

The web client gains `scope` on `WorkflowItem` and passes `scope` to the CRUD
helpers; the combined list keys rows by `scope + name`. Creating a workflow uses
a Global/Project toggle (default Project); existing workflows render scope as a
read-only badge and edits preserve scope.

## Alternatives Considered

### Alternative 1: Parallel `/global-workflows` route tree

- **Description**: Add separate `/global-workflows` (+ `/:name`) endpoints; the
  web client fetches both lists and merges them client-side.
- **Pros**: Keeps each route tree single-purpose; no `scope` param.
- **Cons**: Duplicates four route definitions and their handlers; pushes merge
  logic and two-request orchestration into the client; doubles the OpenAPI
  surface and tests.
- **Why rejected**: More surface and duplication for the same behavior; the merge
  belongs server-side to produce one combined response.

### Alternative 2: Per-scope list, client-side merge

- **Description**: Keep `GET /workflows` project-only; add `?scope` only to a
  separate global list call; merge in the web client.
- **Pros**: Minimal change to the existing list handler.
- **Cons**: Two round-trips for one list; the "combined list" concept lives only
  in the client, so non-web consumers can't get it.
- **Why rejected**: The combined list is a first-class product concept; it should
  be the server's response, not a client assembly.

## Consequences

### Positive

- One route tree, one combined response; the web client renders it directly.
- Back-compatible: omitting `scope` preserves today's project behavior, so
  existing callers and tests keep working.
- Reuses name validation, atomic writes, and the run-active guard unchanged.

### Negative

- The list handler now reads two directories and tags results, slightly more
  complex than the single-directory read today.
- `WorkflowItem` and the CRUD helpers carry a new `scope` field that every
  consumer must thread through.

### Risks

- **Default-scope ambiguity**: a caller omitting `scope` on CRUD silently targets
  project scope. Mitigation: document the default; the web client always sends an
  explicit scope.
- **Cross-scope name confusion**: same-named items in both scopes. Mitigation:
  scope badge in the UI and `scope + name` row keys (already required by PRD).

## Implementation Notes

Add `WorkflowScopeSchema = z.enum(["global","project"])`; extend
`WorkflowsQuerySchema` (and CRUD query) with `scope: WorkflowScopeSchema.optional()`
and `WorkflowItemSchema` with `scope`. A `resolveScopedWorkflowsDir(scope, cwd, env)`
helper centralizes directory selection between the global dir (ADR-002) and
`<cwd>/workflows`. The list handler reads both directories, tags each entry, and
concatenates.
