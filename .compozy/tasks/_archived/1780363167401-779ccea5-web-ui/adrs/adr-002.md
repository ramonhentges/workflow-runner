# ADR-002: Restructure repository into a Turborepo monorepo with a separate web app

## Status

Accepted

## Date

2026-05-31

## Context

The web UI must be a standalone project at the repository root — not nested
inside `src/` — with its own `package.json` and independent build. Today the
repository is a single Bun package (`workflow-runner`) housing the CLI, daemon,
and TUI. Introducing a second deployable (the web app) alongside the existing
runner requires a coordinated way to install, build, type-check, and run both
projects.

The user mandated that both the existing root project and the new web UI be
managed with **Turborepo**, and that the web UI use **React, TanStack Router,
shadcn, and Zustand**. This ADR records the structural decision (a workspace
monorepo) since it changes the shape of the whole repository, beyond the web
app itself.

## Decision

Convert the repository into a **Turborepo-managed monorepo** with the existing
runner and the new web UI as sibling workspace packages, each with its own
`package.json`. Turborepo orchestrates shared tasks (build, typecheck, dev,
test) across both packages. The web UI is a new top-level package built with
React + TanStack Router + shadcn + Zustand, consuming the daemon's HTTP/WS API
over loopback.

## Alternatives Considered

### Alternative 1: Web app nested inside the existing package

- **Description**: Add the UI under the current `src/` tree or a subfolder of
  the existing package.
- **Pros**: No restructuring; single install.
- **Cons**: Violates the explicit requirement for a separate root-level project
  with its own `package.json`; couples frontend and backend build/dependency
  graphs.
- **Why rejected**: Directly contradicts stated requirements.

### Alternative 2: Two fully separate repositories

- **Description**: Keep the runner repo as-is and create a new, independent
  repo for the web UI.
- **Pros**: Maximum isolation.
- **Cons**: No shared task orchestration; harder to version, run, and test the
  two together; contradicts the "managed with Turborepo" requirement.
- **Why rejected**: The user explicitly wants both projects managed together
  with Turborepo.

## Consequences

### Positive

- Clean separation: independent `package.json`, dependencies, and build per
  project, run from one repo with unified commands.
- Room to add further packages (e.g., a shared API-types package) later.

### Negative

- One-time restructuring of the existing repository layout and scripts.
- Contributors must learn the monorepo task workflow.

### Risks

- The existing project uses Bun as runtime/test runner; the monorepo must
  preserve Bun-based workflows for the runner while supporting the web app's
  toolchain. *Mitigation*: validate both task graphs during TechSpec/setup;
  this is a technical detail deferred to the TechSpec.

## Implementation Notes

Concrete workspace layout, package manager, Turborepo pipeline configuration,
and how the runner's existing Bun scripts are wired into the pipeline are
implementation details to be resolved in the TechSpec.
