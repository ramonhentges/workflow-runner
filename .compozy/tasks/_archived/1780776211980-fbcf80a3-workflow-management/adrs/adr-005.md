# ADR-005: Live IDE catalog discovery via a lightweight ACP probe, graceful by design

## Status

Accepted

## Date

2026-06-03

## Context

A step's valid `agent` and `model` values are defined by its `ide`. The only
authoritative source is the running IDE: the app already learns an IDE's agents
from a live ACP `newSession` response (`availableModeIds` in `ide-profiles.ts`),
and the SDK's `NewSessionResponse` also carries `models.availableModels`. The
editor needs to fetch these per IDE (PRD ADR-002) without blocking authoring,
and degrade cleanly when the IDE is absent, unauthenticated, or slow.

## Decision

Add a **single combined discovery endpoint**, `GET /ide/{ide}/catalog?cwd=`,
returning both agents and models from **one probe**. The probe is a new
infra-layer function (`src/infra/acp/ide-catalog.ts`,
`probeIdeCatalog(ide, cwd, spawnFn)`) that reuses `resolveIdeProfile` + the
existing spawn/ACP machinery in a stripped-down form: spawn the profile command,
`initialize`, `newSession({ cwd, mcpServers: [] })`, read agents via the existing
`availableModeIds(result)` and models via `result.models?.availableModels`, then
dispose the subprocess (SIGTERM→SIGKILL, as `AgentSession.dispose`).

The probe is wrapped in a **hard timeout**. Any failure (spawn error, missing
binary, auth required, timeout, malformed response) resolves to a
**graceful HTTP 200** payload `{ reachable: false, agents: [], models: [], reason }`;
success returns `{ reachable: true, agents: [{id,name}], models: [{id,name}] }`.
The endpoint never returns 5xx for an unreachable IDE, so the editor falls back
to manual entry on `reachable: false`.

## Alternatives Considered

### Alternative 1: Error HTTP status on failure

- **Description**: Return 502/504 when the IDE can't be reached or times out.
- **Pros**: Cleaner HTTP semantics.
- **Cons**: Forces the client to special-case error vs empty; "unreachable" is a normal, expected state here, not an error.
- **Why rejected**: Graceful 200 + `reachable` flag models the domain better and simplifies the client.

### Alternative 2: Separate `/agents` and `/models` endpoints

- **Description**: Two endpoints, one per dimension.
- **Pros**: More granular.
- **Cons**: Spawns the IDE twice per step edit; contradicts the single-probe decision (PRD ADR-002).
- **Why rejected**: Doubles cost for no benefit.

### Alternative 3: Reuse the full `AgentSession.start`

- **Description**: Drive discovery through the existing run session factory.
- **Cons**: `AgentSession.start` wires MCP servers, step tokens, kickoff prompts, and outcome races irrelevant to discovery, and asserts HTTP MCP capability.
- **Why rejected**: Too heavy; a purpose-built minimal probe is clearer and safer.

## Consequences

### Positive

- One endpoint, one probe, reflects exactly what the IDE supports now.
- Best-effort by construction: never blocks or breaks authoring; manual entry always works.
- Reuses profile registry and dispose semantics already proven for runs.

### Negative

- Each probe spawns a subprocess, so discovery is slower than a static list and depends on the IDE being installed/authenticated locally.

### Risks

- A hung IDE process. *Mitigation:* hard timeout plus the existing SIGTERM→SIGKILL dispose; the probe is fire-and-forget per request, no caching to leak state.
- An IDE requiring interactive auth. *Mitigation:* probe fails fast → `reachable:false` with a reason; user types values manually.
- `newSession` requiring a valid `cwd`. *Mitigation:* use the request's `cwd` (already validated elsewhere); failure degrades gracefully.

## Implementation Notes

- New route file `src/app/api/routes/ide-catalog.ts`; response schema in `schema.ts` (`IdeCatalogSchema`).
- No caching this phase (PRD ADR-002). Timeout value chosen during implementation (start ~10s) and surfaced in the probe, not the route.
- Unknown `{ide}` → 400 (reuse `UnknownIdeError`/`resolveIdeProfile`), distinct from `reachable:false`.
