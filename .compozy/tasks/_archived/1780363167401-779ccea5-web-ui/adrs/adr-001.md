# ADR-001: Web UI product shape — Operator Console

## Status

Accepted

## Date

2026-05-31

## Context

The workflow-runner daemon already exposes a complete HTTP/WS API (run list,
run detail, start, stop, retry-step, historical events, and a `WS
/runs/:id/attach` channel that streams live events and accepts interactive
input). Today the only client is the terminal CLI/TUI. The user wants a
browser-based interface to operate runs — start, stop, retry, attach, and chat
— without leaving the machine.

The decision is about the *product shape* of that interface for the MVP: how
much of the run-management surface to expose and how the experience is
organized. The technology choices (React, TanStack Router, shadcn, Zustand,
Turborepo monorepo) are fixed inputs and are addressed in ADR-002; this ADR is
purely about product scope and UX framing.

## Decision

Build an **Operator Console**: a single-user, loopback-only control plane with
a persistent app shell containing two anchors —

1. a **working-directory (cwd) switcher** for managing and fast-switching
   between multiple project directories (persisted in the browser), and
2. a **live run dashboard** listing all active and recent runs with
   auto-updating status.

From a selected cwd, a Start-run flow lets the user pick a workflow from that
directory's `./workflows` folder or enter a path manually. Drilling into a run
opens a **live run view** with a streaming chat + interactive input box, a
step-progress indicator, inline stop/retry controls, and a final summary panel.

The MVP delivers the complete operate loop end-to-end. Workflow authoring and
full step-graph visualization are explicitly excluded.

## Alternatives Considered

### Alternative 1: Minimal Launcher

- **Description**: A start form, a flat run list, and a chat view only.
- **Pros**: Fastest to ship; smallest surface area.
- **Cons**: No cwd management, no step-progress indicator, no summary panel —
  all of which the user explicitly requested.
- **Why rejected**: Under-delivers against stated requirements.

### Alternative 2: Rich Observability Suite

- **Description**: Operator Console plus workflow graph visualization,
  run-history analytics/comparison, and desktop notifications.
- **Pros**: Strongest long-term observability story; competitive with
  Temporal/Inngest dashboards.
- **Cons**: Pulls in authoring-adjacent work that was explicitly excluded;
  large scope; violates YAGNI for a first release.
- **Why rejected**: Over-scoped for the MVP; valuable pieces are deferred to
  later phases.

## Consequences

### Positive

- Covers every capability the user described (cwd management, start/stop/retry,
  attach + chat, step progress, summary) without scope creep.
- Maps cleanly onto the existing backend API; minimizes new backend work.
- Mirrors proven control-plane patterns (dashboard + focused run view).

### Negative

- No workflow authoring or graph visualization in the MVP; users still edit
  workflow JSON outside the UI.
- "Dashboard + one focused run" ends a run's live stream when the user
  navigates away (no simultaneous multi-attach).

### Risks

- Listing a cwd's `./workflows` requires a backend capability the daemon does
  not currently expose. *Mitigation*: treated as an explicit dependency in the
  PRD; manual-path entry works without it as a fallback.
- Loopback-only scope limits the UI to the local machine. *Mitigation*:
  accepted intentionally; remote access is a non-goal.

## Implementation Notes

The web UI consumes the existing API surface in `src/app/api/`. The cwd-listing
dependency should be scoped during TechSpec; until then, manual-path entry is
the unblocked path for starting runs.
