# ADR-001: V1 scope and architectural shape for the HTTP+WebSocket API

## Status

Accepted

## Date

2026-05-28

## Context

The workflow-runner daemon currently exposes JSON-RPC over a Unix domain socket. Consumers are the local CLI and a TUI (`@opentui/core`). The daemon owns a mature `RunManager` and `EventLog` with monotonic per-run sequence numbers, a 1000-entry ring buffer, and race-fixed subscribe/backlog ordering (`e35379a`, `d75c3b7`).

We want to add an HTTP + WebSocket API so a future web UI can match TUI capabilities. The V1 ships the API only — no UI is being built yet. The user has locked four constraints:

1. Full parity with the current JSON-RPC surface (intent).
2. `attach` and `send` over WebSocket (chat-style); other methods over HTTP.
3. Localhost-only, no auth in V1.
4. Mount inside the existing daemon process.

A 4-advisor council (Architect, Pragmatic Engineer, Devil's Advocate, Thinker) debated four axes: transport split, framework, in-process vs gateway, and V1 scope discipline.

## Decision

**V1 ships an HTTP + WebSocket API mounted inside the daemon as a thin adapter over a new transport-agnostic application-service layer.**

Concrete scope:

- **Endpoints** — `GET /runs`, `GET /runs/:id`, `POST /runs` (start), `POST /runs/:id/stop`, and `WS /runs/:id/attach` (carries `fromSeq` resume, live event tail, and chat-style `sendInput` frames). Retry-step, doctor, daemon.shutdown, and `ps all=true` are deferred until a real consumer surfaces a need.
- **Framework** — Hono with Zod schemas; `zod-to-openapi` generates the OpenAPI doc as a byproduct. WS framing documented in a short markdown (~30 lines); skip AsyncAPI ceremony for V1.
- **Architecture** — extract a transport-agnostic application-service module that both the existing JSON-RPC server and the new HTTP/WS server consume. No business logic in route handlers. Shared Zod DTOs (`Run`, `RunEvent`, `AttachFrame`) live in a single source of truth used by both transports.
- **Security baseline (non-negotiable)** — explicit IPv4 `127.0.0.1` bind, post-listen assertion that the bound address is not `::` or `0.0.0.0`, `Host` header allowlist on HTTP, `Origin` allowlist on WS upgrade, and one CI test that simulates DNS rebinding (`curl -H 'Host: evil.com'` → 403).
- **Operational guardrails** — max-connections cap, per-connection idle timeout, bounded outbound WS buffer that closes on overflow. No drop-policy semantics yet.
- **Conformance** — one round-trip test: a recorded event log goes through Zod and the TUI parse still renders it. Fails the build on drift between JSON-RPC and HTTP/WS encodings.

## Alternatives Considered

### Alternative 1: SSE for event tail + WS for input (Docker-style two-shape)

- **Description**: Two endpoints — `GET /runs/:id/events` (SSE, `Last-Event-ID` resume mapping to `fromSeq`) and `WS /runs/:id/input` (interactive frames). Mirrors the Docker `/events` vs `/attach` split.
- **Pros**: Free browser-native `EventSource` reconnect; HTTP/2 multiplexing; proxy-friendly; backpressure of outbound events isolated from inbound input liveness; SSE side survives a future gateway extraction unchanged.
- **Cons**: Two reconnect stories, two framing formats, two integration-test matrices for one consumer class (a Bun TUI on localhost). No browser, no proxy, no second maintainer is on the roadmap to amortize the cost.
- **Why rejected**: Council partial-conceded — SSE will be mandatory the moment a browser or long-replay window arrives, but is premature for V1. Decision: ship WS-only now, keep `EventLog.readEventsSince` callable from a future SSE handler without re-plumbing `RunManager`. Flagged as the primary V2+ stretch.

### Alternative 2: Separate gateway process speaking HTTP/WS to clients and JSON-RPC over UDS to the daemon

- **Description**: A new long-running process bridges HTTP/WS clients to the existing UDS JSON-RPC daemon. Daemon stays untouched.
- **Pros**: Zero coupling to daemon lifecycle; HTTP/WS crashes don't take CLI/TUI down; clean process-level isolation for security and resource limits.
- **Cons**: Two processes for a single-maintainer dev tool means two supervisors, two log streams, two restart stories, two upgrade paths. Adds a JSON-RPC round-trip to every API call. No real consumer is asking for the isolation today.
- **Why rejected**: Premature for V1. Made cheaply reversible by the application-service layer: extracting a gateway later becomes a 1-day refactor rather than a rewrite.

### Alternative 3: Versioned event/command schema as the V1 deliverable (no endpoints yet)

- **Description**: Ship a `domain/api-schema.ts` with versioned Zod schemas + conformance tests against the JSON-RPC surface. No HTTP/WS endpoints until a real consumer arrives.
- **Pros**: Defends against contract-promotion / speciation risk. Schema becomes the integration surface for any future consumer.
- **Cons**: A spec without a consumer rots as fast as endpoints without a consumer. Conformance tests against a hypothetical client test the spec, not the system. Doesn't unblock the future UI work the user actually wants to enable.
- **Why rejected**: The Thinker (proposer) withdrew the "spec-first" framing during rebuttal and partial-conceded. Captured instead as a *byproduct* of the chosen path: shared Zod DTOs + auto-OpenAPI + one round-trip conformance test.

### Alternative 4: Full JSON-RPC parity (all 8 methods) + AsyncAPI 3.0 + bearer auth in V1

- **Description**: Match the JSON-RPC surface exactly, ship a hand-written AsyncAPI 3.0 spec for the WS channel, add bearer-token auth.
- **Pros**: No "what's missing?" question for a future UI; fully documented; remote-ready.
- **Cons**: Gold-plating for a consumer that doesn't exist; AsyncAPI codegen tooling is still rough; bearer auth without a remote use case is premature hardening; doubles the V1 build cost.
- **Why rejected**: The Pragmatic Engineer's "thinnest credible slice" carried the council. Each deferred piece is additive, not breaking.

## Consequences

### Positive

- Future web UI development is unblocked by a documented, conformance-tested API surface.
- A clean application-service seam keeps `RunManager` ignorant of transport, enabling SSE, a gateway process, or a third adapter to be added without core refactors.
- Shared Zod schemas + auto-OpenAPI close the speciation gap between JSON-RPC and HTTP/WS at low cost (~half-day).
- Security baseline addresses DNS rebinding, IPv6 bind footguns, and shared-host exposure with one-shot controls that don't degrade local UX.
- WS-only carries both interactive and autonomous runs with one reconnect path, one framing format, one debug story.

### Negative

- Daemon process now owns one more responsibility (HTTP/WS listener). Shutdown ordering and event-loop sharing must be deliberate.
- `JSON-RPC source of truth` vs `vocabulary source of truth` was an unresolved tension. If implementation drifts toward direct route → `RunManager` calls, speciation risk re-emerges.
- WS-only means autonomous read-only consumers (future dashboards) carry WS reconnect/heartbeat ceremony they don't need until SSE lands.

### Risks

| Risk | Mitigation |
|---|---|
| Application-service layer becomes thin wrapper, then HTTP routes start calling `RunManager` directly → speciation | Speciation guard: a third hypothetical adapter (test-only stdin/stdout adapter) must drive the service without `RunManager` changes before merge. |
| WS or HTTP handlers block the event loop, starving JSON-RPC for CLI/TUI | Integration test: N idle WS connections + `daemon.doctor`/`run.ps` p95 latency under 5 ms. |
| WS resume across mid-flush disconnect re-introduces the gap-closing race in a new shape | Re-verify `fromSeq` semantics explicitly against WS lifecycle (close codes, reconnect, missed events) — do not assume the JSON-RPC subscriber fix transfers. |
| Schema drift between JSON-RPC encoding and HTTP/WS encoding | Round-trip Zod conformance test on every CI build. |
| Shutdown closes the listener before draining open WS clients (current daemon shutdown does this) | Shutdown sequence: stop accepting new connections → send close frame to WS clients → wait briefly for graceful close → existing daemon teardown. |
| WS send queue grows unbounded for a stalled slow client | V1: max-connections cap + idle timeout + bounded outbound buffer with close-on-overflow. Defer drop-policy design to V2. |

## Implementation Notes

- New module: `src/app/api/` for the Hono server, route handlers, and WS upgrade handler. Per CLAUDE.md, `app/` is for entry-point dispatch and route shape — keep handlers thin.
- New module: `src/domain/app-service.ts` (or similar) — transport-agnostic operations (`startRun`, `listRuns`, `getRun`, `stopRun`, `attachRun`, `sendInput`) consumed by **both** the existing UDS JSON-RPC server and the new HTTP/WS server. JSON-RPC handlers (`src/infra/daemon/handlers/*`) get refactored to delegate here.
- Shared DTOs: `src/domain/api-schema.ts` — Zod definitions for `RunSummary`, `RunDetail`, `RunEvent`, `AttachFrame` (server→client), `InputFrame` (client→server). Reused by JSON-RPC notification shapes.
- OpenAPI: emitted at `/openapi.json` by Hono + `@hono/zod-openapi`.
- WS framing doc: `docs/ws-protocol.md` (~30 lines) — frame envelope, `fromSeq` semantics, close codes, heartbeat cadence.
- Security: port number is fixed (configurable via daemon flag); bound to `127.0.0.1` only; startup asserts `server.address().address === '127.0.0.1'`. `Origin` allowlist on WS upgrade rejects anything that is not `null` (curl/non-browser) or `http://127.0.0.1:<port>` / `http://localhost:<port>`. `Host` header allowlist on HTTP rejects anything not in the same set.
- Daemon shutdown extends `makeShutdown()` (currently in `src/commands/daemon.ts:250–273`) to drain WS connections before closing the UDS listener.
