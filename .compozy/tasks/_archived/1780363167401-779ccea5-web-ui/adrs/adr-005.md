# ADR-005: Frontend data architecture — TanStack Query for server state, Zustand for client state, a dedicated WS client for the live stream

## Status

Accepted

## Date

2026-05-31

## Context

The web UI must show a live-updating run dashboard, run detail, and a live
"chat" stream for a focused run, while persisting the user's working-directory
(cwd) list in the browser. The PRD names React, TanStack Router, shadcn, and
Zustand. Server data (runs, detail, health, workflow listing) has different
lifecycle needs (caching, refetch, invalidation) than client/UI state (cwd
list, active cwd, transient UI), and the live run stream arrives over a
WebSocket rather than request/response.

## Decision

Split state by nature:

- **TanStack Query** owns server state fetched over HTTP — `GET /runs`
  (with `?cwd=` / `?all=`), `GET /runs/:id`, `GET /workflows?cwd=`,
  `GET /health` — with background refetch and invalidation after mutations
  (`POST /runs`, stop, retry-step).
- **Zustand** owns client state: the persisted cwd list + active cwd (via
  `persist` to `localStorage`) and transient UI state.
- A **dedicated WebSocket client** (a small typed wrapper + a React hook) opens
  `/runs/:id/attach`, parses `AttachFrame`s with local zod schemas mirroring
  the server's `schema.ts`, and reduces them into a view model (snapshot,
  ordered transcript, run status, interactive-enabled flag, summary). The
  transcript coalesces consecutive `stream` chunks of the same kind into one
  message block; `banner` events start step sections; `status`/`log` render as
  lines; `summary` also feeds the final summary panel.

Wire types are redeclared in `web/src/lib/api` (TS types + minimal zod for
frame validation) rather than imported from the runner package, decoupling the
React/Vite build from the runner's Node/Bun internals.

## Alternatives Considered

### Alternative 1: Zustand only (plain fetch + manual polling)

- **Pros**: Stays strictly within the PRD's named libraries.
- **Cons**: Hand-rolled caching, refetch, and invalidation; more bespoke code.
- **Why rejected**: Reinvents what TanStack Query provides.

### Alternative 2: TanStack Router loaders for server data

- **Pros**: No extra library; uses the mandated router.
- **Cons**: Weaker background refetch / live invalidation ergonomics than Query.
- **Why rejected**: Query is the better fit for a frequently-changing dashboard.

### Alternative 3: Share a generated types package between runner and web

- **Pros**: Single source of truth for wire types.
- **Cons**: New package; couples builds. YAGNI for the MVP.
- **Why rejected**: Redeclared types + the existing `openapi.json` conformance
  test are sufficient.

## Consequences

### Positive

- Idiomatic separation; minimal hand-written caching logic.
- WS view-model reducer is unit-testable in isolation.

### Negative

- Adds TanStack Query beyond the PRD's named stack.
- Wire types are duplicated, risking drift from `schema.ts`.

### Risks

- Type drift between `web/src/lib/api` and `src/app/api/schema.ts`.
  *Mitigation*: keep redeclared types minimal; the daemon's `openapi.json` is
  the cross-check reference.

## Implementation Notes

The focused run view subscribes to the WS client; navigating away closes the
socket (no multi-attach, per ADR-001). Reconnect/resume via `fromSeq` is a
non-goal for the MVP.
