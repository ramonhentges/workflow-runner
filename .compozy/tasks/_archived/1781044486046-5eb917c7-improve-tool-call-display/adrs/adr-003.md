# ADR-003: Derive the tool-call summary in the domain and ship it in the event

## Status

Accepted

## Date

2026-06-08

## Context

A tool-call entry must show a human-readable summary derived from ACP fields:
the command for shell/`execute` calls (from `rawInput`), the affected file for
`read`/`edit` calls (from `locations`), and a `title`/`kind` fallback when
specifics are absent. A short error reason is needed on failure. This mapping
must look identical in the CLI and the web UI (ADR-001's parity goal), across
all four IDE profiles whose data richness varies.

The codebase is hexagonal: pure business logic lives in `src/domain/`, with a
port introduced only when a second implementation exists. Both render surfaces
are TypeScript, but the web client is a separate workspace that cannot import
domain code directly — it validates events through a Zod schema.

## Decision

A pure domain function `summarizeToolCall` (new file `src/domain/tool-call.ts`)
maps the ACP-derived inputs to a complete display view
(`status`, `kind`, `title`, optional `errorText`). The ACP `AgentSession`
calls it and emits a `tool_call` `RunnerEvent` carrying that precomputed view;
the view is persisted as part of the event. Both the TUI and the web UI render
the precomputed `title`/`errorText` verbatim — neither re-derives anything.

The persisted view carries only display fields (no `rawInput`, `rawOutput`, or
`content` blobs); error text is extracted at emit time and shipped as a short
string.

## Alternatives Considered

### Alternative 1: Each renderer formats its own summary

- **Description**: Ship raw ACP fields and let the TUI and web each format.
- **Pros**: Per-surface flexibility.
- **Cons**: Duplicates the mapping in server TS and web TS; guarantees eventual
  drift; bloats every persisted event with raw blobs.
- **Why rejected**: Directly violates the single-shared-model parity goal and
  the minimal-payload decision.

### Alternative 2: Derive in the web Zod layer / a web util

- **Description**: Keep the server dumb; compute the summary client-side.
- **Pros**: No server-side formatting.
- **Cons**: The TUI would still need its own copy; replay would depend on
  client version rather than what was computed live.
- **Why rejected**: Splits the logic across surfaces and makes history
  version-dependent.

## Consequences

### Positive

- One authoritative mapping; CLI and web are identical by construction.
- The web client stays a thin renderer of precomputed strings.
- Replay shows exactly the summary computed at run time.
- Pure function is trivially unit-testable in isolation.

### Negative

- Adds a small domain module and a corresponding field to the persisted event.
- Phase 2 (expandable raw detail) will need to add fields and re-instrument,
  since raw inputs are deliberately not persisted now.

### Risks

- The web Zod schema must mirror the emitted `tool_call` shape; a mismatch
  silently drops the event (existing `safeParse` behavior). Mitigated by a
  schema parse test fixture covering the new event.

## Implementation Notes

- `summarizeToolCall` relativizes file paths against the run `cwd` and applies
  sensible truncation to long commands/paths.
- Path/command/error extraction reads optional ACP fields defensively and falls
  back to `title`, then `kind`, then a generic label.
