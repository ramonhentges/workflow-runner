# ADR-006: Attach Replay via Per-Run Ring Buffer + Disk Fallback

## Status

Accepted

## Date

2026-05-25

## Context

When a TUI attaches to a running run, it must replay enough of the recent event history that the user sees coherent context — at minimum, the current step's events from its `banner` onward, so the user understands what step is in progress and what the agent has been doing.

Two extremes are easy to specify and wrong in different ways:

- Always read from disk: every attach reads `events.jsonl` from the last `banner` event forward. Simple (one code path) but attach latency is dominated by disk I/O and grows with the size of the current step's backlog. With the `thought`-filtered log staying small in practice, this is *probably* fine — but "probably" isn't a useful guarantee for the PRD's "< 1 second to first paint" target.
- In-memory only: maintain only a per-run buffer; no disk read on attach. Fast but new TUIs attaching after a daemon restart see no backlog, breaking the recovery story.

The pragmatic middle: per-run ring buffer (bounded memory for instant replay during normal operation) with disk fallback when the buffer is insufficient (e.g., after a daemon restart, or for a very long step).

Ring buffer sizing: typical agent steps emit dozens to low-hundreds of events (mostly `log` and `stream` of kind `message`; `thought` streams are filtered out at the log level per ADR-001). A 1000-event buffer per run holds ~10 MB at the upper end of realistic event sizes, which is generous; concurrent runs at the V1 target (4 active) cap memory at 40 MB for replay buffers. Fine.

The disk fallback path requires reading `events.jsonl`, locating the last `banner` event for the current step, and streaming events forward. This is straightforward: parse line by line, find the last `{"type":"banner","stepId":<current>}`, stream from there.

## Decision

Each active `Run` maintains an in-memory ring buffer of its most recent **N = 1000** events. The buffer is appended to in lockstep with the disk event-log writer (same order, same content). On `run.attach`, the daemon:

1. Looks up the run's ring buffer.
2. If the buffer contains a `banner` event for the run's current step, replays events from that banner forward over the JSON-RPC notification channel, then transitions to live-streaming.
3. If the buffer does **not** contain the current step's banner (daemon was restarted, or step is unusually long), opens `events.jsonl`, scans backward to find the last `banner` for the current step, streams events from there forward, then transitions to live-streaming.

The ring buffer is reset to empty when a new `banner` event is emitted (since the previous step's events are no longer needed for current-step replay; older events remain on disk for post-mortem).

## Alternatives Considered

### Alternative 1: Always read from disk

- **Description**: Every `run.attach` reads `events.jsonl`, locates the current step's banner, streams forward.
- **Pros**: Single code path; no in-memory buffer to keep in sync; no memory cost.
- **Cons**: Attach latency is bounded by disk I/O speed and the size of the current step's backlog; no upper bound on attach latency under sustained heavy logging.
- **Why rejected**: The "< 1 second to first paint" PRD target is hard to guarantee without an in-memory path; the ring buffer is cheap enough to be worth the dual-path complexity.

### Alternative 2: In-memory only

- **Description**: Replay strictly from the ring buffer; if the buffer doesn't have the current step's banner (because the daemon restarted), show nothing — the user sees only live events from attach forward.
- **Pros**: One code path; no disk I/O on attach.
- **Cons**: Defeats the recovery story: after a daemon restart you can't see what step is running until the next event arrives. For a long autonomous step that may be ten minutes between events.
- **Why rejected**: The post-restart attach case is exactly the recovery scenario the daemon exists to serve well.

### Alternative 3: Larger ring buffer (e.g., 100,000 events)

- **Description**: Push the ring buffer big enough to hold full step histories so disk fallback is rare.
- **Pros**: Disk-fallback path is exercised only after a daemon restart.
- **Cons**: Memory cost scales with both buffer size and concurrency; an outlier run with large event payloads can blow memory budgets; the disk path must work correctly regardless, so we don't actually save code by making it rare.
- **Why rejected**: 1000 events covers normal operation; the disk path is mandatory anyway; bigger buffer only delays inevitable correctness work on the disk path.

## Consequences

### Positive

- Attach latency in the common case is bounded by JSON-RPC round-trip + in-memory iteration — well under the 1 s PRD target.
- After a daemon restart, attach still works correctly via the disk fallback path.
- The ring-buffer-reset-on-banner rule keeps memory cost tightly bounded regardless of how many steps a run has executed in its lifetime.

### Negative

- Two code paths for replay (memory and disk) that must agree on the format. Mitigated by sharing the same event-formatting function and a single test that asserts both paths produce identical output for the same input log.

### Risks

- **Risk**: The ring buffer and disk log diverge (an event hits one but not the other). **Mitigation**: A single `EventLog.append(event)` method writes to both atomically (buffer first, then disk). If the disk write fails, the daemon logs the error and marks the run `failed` with reason "event log write failure"; events lost in the buffer-vs-disk window are bounded to the single failing append.
- **Risk**: A pathological step emits >1000 events before any attach, so all in-buffer attaches still trigger disk reads. **Mitigation**: 1000 is generous for normal workflows; if real-world usage shows this is too small, the limit is a constant and easily tuned.
- **Risk**: Reading the disk fallback on attach blocks the daemon's event loop briefly. **Mitigation**: Use Bun's async file API (`Bun.file(path).text()` is non-blocking); for large logs the scan is still O(N) bytes but doesn't block; for very long backlogs we accept slower attach as a known fallback cost.

## Implementation Notes

The ring buffer is a small class in `src/infra/daemon/event-log.ts`. Its public surface is `append(event)`, `currentStepBacklog(): RunnerEvent[] | null` (returns `null` when buffer doesn't contain the current step's banner). The daemon's attach handler tries the buffer first, falls back to disk on `null`.
