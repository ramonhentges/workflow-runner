# ADR-001: Merged scope model for global and project workflows

## Status

Accepted

## Date

2026-06-10

## Context

Workflows in workflow-runner are entirely project-scoped. Every list and CRUD
operation requires a working directory (`cwd`) and resolves files under
`<cwd>/workflows/*.json`. There is no way to reuse a workflow across projects
without copying its JSON into each project's `workflows/` folder, which causes
drift and duplication.

Users want a single canonical home for reusable workflows that appears alongside
project workflows in the web UI, can be run against any active project, and can
be created, edited, deleted, and listed like project workflows. The product
answers that shape this decision: reuse is the goal; a global run executes
against the currently active working directory; both scopes appear in one
combined list distinguished by a badge; editing a global workflow is
frictionless; and an active working directory remains the gate for the UI
showing any workflows at all.

## Decision

Introduce **scope** as a first-class property of every workflow: `global` or
`project`. Global workflows live in a single fixed user-level location. The
workflow list surfaces both scopes in one response, each tagged with its scope,
and the web UI renders them as one combined, badged list. Create, edit, and
delete operate on whichever scope an item belongs to. Running a global workflow
uses the active working directory as the run's project context, exactly as a
project workflow run does.

## Alternatives Considered

### Alternative 1: Global as a pinned directory

- **Description**: Model the global store as a special, always-present entry in
  the existing working-directory switcher; reuse all current per-cwd endpoints
  unchanged. "Global" becomes just another directory the user switches to.
- **Pros**: Minimal change; reuses existing list/CRUD machinery as-is.
- **Cons**: The user would *switch to* globals rather than see them combined with
  project workflows in one badged list, contradicting the chosen combined-list
  experience and weakening the reuse story.
- **Why rejected**: Fails the core UX requirement that both scopes appear
  together, distinguished by a badge.

### Alternative 2: Layered overlay with precedence

- **Description**: A single namespace where a project workflow with the same name
  overrides the global one, mirroring git/Claude config scope precedence.
- **Pros**: Familiar config-scope pattern; elegant for power users.
- **Cons**: Adds precedence and collision machinery; hides globals when shadowed
  by a same-named project workflow, contradicting the combined-list intent.
- **Why rejected**: YAGNI for a reuse-focused MVP; introduces complexity the user
  did not ask for and hides workflows the user expects to see.

## Consequences

### Positive

- One canonical home for reusable workflows; no more copying JSON per project.
- Clean mental model: scope is an explicit, visible property of a workflow.
- Running a global workflow reuses the existing active-cwd run semantics, so no
  new run-targeting concept is required.

### Negative

- The list and CRUD surface must thread a scope concept through, rather than
  inferring everything from `cwd`.
- Same-named global and project workflows can coexist; both are shown and
  distinguished by badge, which users must learn to read.

### Risks

- **Ambiguous addressing**: a name could exist in both scopes. Mitigation:
  address workflows by scope explicitly so operations are never ambiguous.
- **Accidental cross-project impact**: editing a global workflow affects every
  project. Mitigation deferred per product decision (frictionless edit chosen);
  the scope badge provides the visual cue.

## Implementation Notes

Storage location, endpoint shape, and addressing scheme are technical concerns
for the TechSpec. This ADR fixes only the product model: scope as a first-class,
visible property, a single global home, a combined badged list, and active-cwd
run semantics for global runs.
